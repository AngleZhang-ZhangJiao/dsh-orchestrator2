# 项目目录及协同开发规范 v2.1

> 适用场景：FDE 工程师（无代码能力）通过多 AI 协同完成新项目从需求到交付的全过程。
> 本文 = 标准目录结构（六区 + 归档区）+ 多智能体协同开发规范（三阶段全流程 + 两场景分支）。
> 每个新项目开工时：① 按第二节建好目录骨架（可先建空目录）；② 将本文件复制到 `00-项目管理/` 下作为项目内规范；③ 从模板集（第十节模板索引）复制所需模板落位。
> **两场景**（v2.1 新增）：**场景1 修改已有系统功能/bug**（设计链变体：现状研究中，见 14.1）；**场景2 技术调研储备搜索**（独立终态调研流程，见 14.2）。两者都以最小侵入嵌入三阶段框架，不新增角色、不动开发/验收转移表、不动预算三硬上限。
> v2.1 变更（相对 v2.0）：**A1** 一次授权多包连跑（关卡2 取消一包一授权；切分标准=能否构成一次有意义的人工测试；两次人工测试之间全自动连跑；测试通过=自动放行后续包；异常硬停；用户可随时喊停）；**A2** 验证审核并入代码审查、全归审核员（开发阶段流水线 7 态收敛为 5 态：待审核→执行中→待审查→待构建→待人工测试；调度员只做机械状态迁移/对账/协调取证）；**B1** 预算按包复杂度分档（小包 4/4/24、大包 8/8/48；任务包生成时标注档位、用户确认）；**C1** grill 开场先问档位（跳过/轻量/标准，缺省不再固定「标准」）；**E** 目录体系演进六项（00-项目管理区/协同区扁平化/测试区骨架/交付区任务级记录/90-历史归档/规范本体入 00 区）；**F1+F2** 两场景扩展（修改已有系统 + 技术调研储备，见第十四节）。原 v2.0 全文保留（旧枚举值全部保留兼容），仅有 v2.1 明确列出的改动。

> v2.0 变更（相对 v1.1）：五区目录体系（新增 04-测试）；角色表新增研究员；三阶段状态机（设计阶段 9 态 + 开发阶段 7 态 + 验收修复循环 5 态 + 收尾）；任务包双区同名对应（设计区任务包 + 协同区状态/证据；状态头 `设计目录` 机器指针）；预算体系（预算基线 + 任务包预算块 + 预算台账）；任务包串行（一包一授权）；验收修复循环含审核员代码审查；设计决策清点协议；`_任务模板/` 双区模板；过程记录 01~04 命名体系；安装包版本号目录管理。原有开发纪律（单一代码写入者、候选 commit、.lock、git status 核查等）原文保留，仅换称谓。

## 一、角色定义

| 模型 | 角色 | 职责 |
|------|------|------|
| 用户 | — | 聊需求、确认设计、授权开发（一次授权多包连跑）、人工测试、确认验收、授权收尾；全部人工关卡最终决定权 |
| 模型A | 调度员 | 需求沟通、搜索调研清单、派发研究员、汇总学习、产品设计、HTML 原型、任务包、机械状态迁移与对账/协调取证、检查修复、构建/更新、收尾。**永不修改目标代码区（任务包 02 指定，缺省 `02-代码/`）** |
| 模型R | 研究员 | 按派工调研单个（或一组）同类产品：功能、设计思路、公开代码与 License，各出一份报告。只读研究；不执行外部代码；不改项目文件 |
| 模型B | 审核员 | 高风险设计可行性复核（条件触发）；计划审核；代码审查（**一次性完成 AC 证据核验（无证驳回）+ 代码审查（含复杂度审查小节）**）；修复代码审查。只读审核，不改方案/原型/代码 |
| 模型C | 开发员 | 按任务包开发、自测（附真实命令输出）、候选 commit；验收阶段修复开发。**目标代码区（任务包 02 指定，缺省 `02-代码/`）唯一默认写入者**，按六档阶梯写最小实现 + `ponytail:` 注释约定 |

**单一代码写入者规则（适用对象 = 目标代码区；新产品任务缺省即 `02-代码/`，行为字面不变）：**
1. 同一时刻只有一个角色可修改**目标代码区**（任务包 02 指定，缺省 `02-代码/`）内的产品代码；默认只有模型C能改。
2. A、B 审核时只读代码，发现问题写明退回 C，禁止审核时顺手修复。
3. 各模型开始工作前必须检查 `git status`、当前分支和基线 commit。
4. 不得覆盖、删除或提交与本任务无关的改动；B 环节 `git status --porcelain` 核查范围/无关改动不得提交的判断范围，均以目标代码区为准（越界即范围漂移）。

**目标代码区（v2.1）**：任务包 02 第二节「涉及文件/模块清单」以其为路径根；缺省值 = `02-代码/`（新产品任务）。场景1（修改已有系统）下 = 现状确认时用户圈定的源码目录集合，记入 01 需求说明（约束节）/ 02 第二节 / 06 定稿记录；**状态头不加新字段**（只复用既有「流程类型」字段）。

**模型钉选纪律：** 任何钉选模型 ID 实施前必须核实（本机 provider 目录/配置）；核实不存在或无凭证立即回报用户选替代，不得静默换模型。`max` 等推理等级（reasoningEffort）不属于模型 ID 的一部分。

### 2.3 双区同名对应规则

- 任务包是**设计产物**（调度员设计、审核员审核的依据），落 `01-设计/<产品任务>/任务包/<TP编号>-<名>/`；
- 该任务包的**状态与过程证据**落 `03-开发协同/<TP编号>-<名>/`，同名同编号；
- 机器链接：`状态.md` 固定头含 `设计目录：01-设计/<产品任务>/任务包/<TP编号>-<名>`，`enter_auto_mode` 顺指针校验任务包文档，不靠人记（场景2 技术调研的 `设计目录` 指 `01-设计/技术调研/<主题>`，**不建 goal、不进开发阶段**）；
- 切线语义：任务包 01/02 是"开发前"的设计产物 → 设计区；工作证据（计划评审/执行自测/代码审查）是"开发中"的证据 → 协同区。**切线正好落在开发授权关卡上**；v2.1 扁平化后三件直放协同区任务根（不再有 `过程记录/` 子目录）；
- "不覆盖、版本递增"规则适用 `01-设计/` 的 04/05/原型/06；**任务包 01/02 豁免**（待修订循环需反复修改）——原地修订并在文末附修订记录（日期+改动摘要+触发环节）；协同区/测试区文件按事实追加更新。

### 2.4 开发协同区定位说明（为什么保留）

模型间沟通分三类：① 任务指派——任务包本身即消息（设计区），派工 prompt 自包含一次性、不落盘；② 研究报告——调研报告已在设计区；③ **工作证据**——审核结论、执行自测记录必须持久化：无证驳回、驳回轮次与 >3 轮裁决、上下文压缩后的证据恢复、责任追溯全靠它。故协同区保留，去掉"待发消息"语义，定位为状态机 + 证据区。

**codegraph 管理对象（v2.1 增注）**：新产品任务 = `02-代码/` 唯一代码区，codegraph 管理；**场景1＝目标代码区随任务包指定，索引建于项目根**（老系统仓库根，覆盖六区脚手架与既有源码目录）。

### 3.6 单一状态源与状态头字段

- `03-开发协同/<TP编号>-<名>/状态.md` 顶部固定格式块是全流程唯一机器状态源，任务包生成时建立，初始 `当前阶段 = 待启动`。
- 状态头字段：当前阶段 / 当前环节负责方 / 任务类型 / **规范版本**（★v2.1 M4 强制：`v2.1` 为本预设唯一合法值；`v1.1` 值显式拒绝并提示改用 1.0 预设；未知值一律拒绝——**不再由「有无设计目录」推断版本**）/ **流程类型**（产品设计全流程 / 仅开发 / **技术调研储备**〔v2.1 场景2 专用，见 §2.3/§3.1b/§11.1〕，缺省仅开发）/ **设计目录**（v2.x 必填，指向 `01-设计/<产品任务>/任务包/<TP编号>-<名>`；场景2 指 `01-设计/技术调研/<主题>`）/ **推进goal / goal状态 / 启动revision**（★v2.1 M3 **预留字段**：当前不回写、一律填 `—`，权威以 goal 工具/台账为准；幂等接线另立项）/ **repairOf / issueId / parentCandidateCommit**（★v2.1 P2-1 修复包归属：仅修复包必填，普通包填 `—`）/ 本环节驳回轮次 / 候选commit / 下一步 / 必读文件 / 最近更新 / 阻塞待办。**不含预算计数字段**——预算记账载体是 预算台账.md（第四节）。

**实测自动推进启动条件（v2.1 · M4，机器 fail-closed）**：`enter_auto_mode` 依次校验 ① 状态.md 固定块可解析且「当前阶段」在枚举内；② `规范版本` 存在、在枚举内、且非 `v1.1`；③ 「流程类型」在枚举内；④ 「设计目录」存在；⑤ 预算台账存在且固定块可解析（**仅「技术调研储备」豁免**）；⑥ 设计目录下 01/02 齐备，`产品设计全流程` 另需上级产品任务目录的 04/06 + `确认版本：vX.Y` + **设计基线哈希逐项核对**（M5）；⑦ 幂等（该任务目录无既有推进 goal）；⑧ 当前阶段=`待审核`；⑨ 单包串行。任一条不成立即拒绝并**点名出问题的文件**，不产生任何副作用。另设**开发准备门禁（v2.1.4）**：`00-项目管理/开发准备.md` 固定块五字段齐备、`必要项` ≥1、`未通过项` = 0、`最近复查` 为日期形态，否则同样 fail-closed 拒绝（见 §4.6）。
- 设计/验收阶段为交互态，调度员对话推进并维护状态，不建 goal；开发阶段才由 `enter_auto_mode` 建 goal，**goal 粒度 = 单包**。
- **两层状态源（v2.1 · M1）**：**产品级** `03-开发协同/<产品任务>/产品状态.md`（固定块：当前设计阶段 / 当前环节负责方 / 活跃任务包 / 任务包清单 / 阻塞待办）承担**设计阶段九态**；**任务包级** `03-开发协同/<TP编号>-<名>/状态.md` 只管**该单包的开发 5 态 + 修复循环 5 态**。开工判定与恢复轮**先读产品状态.md 定位设计期环节，再下钻任务包**；任务包生成 / 验收关闭 / 需求级回退时由调度员回写「活跃任务包」与「任务包清单」。设计中途杀会话后，凭产品状态.md 即可恢复到确切环节。
- **任务包绑定的状态源是 状态.md 顶部固定格式块（唯一机器解析源）**；解析失败或关键字段缺失一律 **fail-closed 拒绝**并点名损坏文件（M4/P2-2 口径，不 JSON 化、保留人读 Markdown）。
- **多包管理（v2.1：一次授权多包连跑）**：任务包生成时全部包初始 `待启动`；**首次**授权后，两次人工测试之间的所有任务包**全自动连跑**，无包间人工关卡——本包人工测试**通过即放行信号**（测试通过 → 调度员核查下一包前置已全部 `已完成` → 置 `待审核` → 再次 `enter_auto_mode`，**无需用户重复说「开始自动推进」**；首个包仍需用户明确授权）。包间衔接走交互态（机械状态迁移 + 前置核查），**不存在 goal 内跨包推进逻辑**（goal 粒度仍=单包）。
- 仅开发旧任务：状态头无 设计目录 字段，任务包文档仍在 `03-开发协同/<任务>/开发计划/`，行为完全不变（enter_auto_mode 走仅开发兼容路径）。

### 3.7 驳回与裁决规则

- **驳回机制**：审核不通过须写明原因，回退上游修复后重审；回退时必须声明哪项已有结论因此失效、需从哪个环节重新执行。普通驳回原因只写过程记录中的审核意见文档，不重复记录。
- **跨改动点冲突扫描（第 4 项）**：计划审核除三项自查外，另按 §3.8 产「跨改动点冲突扫描表」（输入＝02 §三 各改动点的「消费/产出」契约行）；表中判定为包内矛盾的，即构成本节驳回（状态 待修订）。
- 同一环节最多 3 轮；同一环节驳回超过 3 轮 → 由负责模型生成**非技术化决策简报**（记入 `决策记录.md`，分歧类：当前卡点、重复失败根因、方案一/二成本与风险、推荐方案及理由、是否建议缩小需求/换模型/请真人工程师介入）→ 交用户裁决（选方案/调整需求/更换模型/终止任务），并更新 `状态.md` 阻塞/待办字段注明时间。
- **需求变更流程**：开发中途需求变更 → 记入 `决策记录.md`（变更类）→ 状态回 `待修订` → 调度员修订任务包 → 已做的审查/测试结论按需声明失效并重新执行受影响环节（受影响分支需重跑第九节决策清点，已清零分支保留）。

### 3.8 跨改动点冲突扫描（计划审核第 4 项，TP-A1 · D2）

**定位**：计划审核在原有三项（任务包与需求逐条对照 / 改动范围与 codegraph 一致 / 验收标准可测试）之外的**第 4 项**。任务包 02 §三 每个改动点必须写「消费/产出」契约行（见 `_任务模板/02_开发方案与任务包.md` §三），契约的**接口五类**为：代码符号 / 工具与 schema / 状态字段 / 文件格式 / 标识关系。扫描的输入就是这些契约行——**没有契约就没有扫描**。

**方法**：读 02 各改动点的契约行 → **逐对比较**（D1~Dn 两两）→ **只扫确实共享的组合**（共享项落在上述五类接口中）→ 逐行产表：

| 改动点A | 改动点B | 共享项 | A产出 | B消费 | 发现 | 处置 |
|---|---|---|---|---|---|---|
| D1 | D2 | 五类接口中的哪类、哪个具体符号/字段/格式 | A 契约行声明的产出 | B 契约行声明的消费 | 一致 / 命名或签名不符 / 语义不符 / 缺失 / 循环依赖 | 按下方处置规则 |

- **无共享组合时**：写「无共享项（已核查 D1~Dn 两两关系）」，不得省略核查动作，也不得机械 O(n²) 罗列无共享的组合。
- **落点**：扫描表写入协同区 `计划评审-vX.Y.md`（小节「跨改动点冲突扫描表」）。
- **处置规则（三条）**：① 包内矛盾（A 产出与 B 消费不符）→ **驳回计划**（状态回 待修订）；② 与冻结设计/显式需求冲突 → **回设计**（或用户裁决）；③ **调度员不得自行裁定技术冲突**——技术冲突的取舍归设计或用户，调度员只做机械状态迁移与对账。

## 四、预算口径（次数台账 + token 统计）

> 预算口径说明（用户为 Coding Plan 订阅、不按量付费）：**硬上限 = C/B 运行次数 + 调度员工作轮三项；统计信号 = token 用量（不作停机依据）；全程无费用概念**（否定式表述如「不统计费用」「不作金额换算」允许存在）。
> 控制原理：消耗主体是子代理运行（C 一次大上下文会话），不是调度员轮数；轮数已由「前景阻塞派工」恢复为工作步计数，见 3.7 与第九节。**控制手段 = 三种**：① 开发/验收阶段 B/C 派工为后台派工、调度员同一 goal 轮内看门狗 tick 循环（循环在轮内、不烧 goal 轮，消除空转轮）；② 预算块 + 预算台账（次数硬上限，**按包复杂度分档**）；③ 可选真实 token 计量（仅统计）。

### 4.1 预算基线（03-开发协同/预算基线.md，v2.1 按包复杂度分档）

- 用户维护的默认预算档，开工时建一次；**不含任何价格内容**。
- **分档（决策#22，v2.1）**：**小包** C 运行 ≤4 / B 运行 ≤6 / 调度员工作轮 ≤24；**大包** C 运行 ≤8 / B 运行 ≤8 / 调度员工作轮 ≤48。
  - **任务包生成时由调度员标注档位**（写入任务包 02 §预算块），**用户确认**后生效；关卡2 前用户可见可改（现场扩档需记入 决策记录.md 裁决类）。
  - 缺省档 = **小包 4/6/24**；基线缺失时按本节内置默认档继续，并在预算台账标注「按规范内置默认档」。
- 其他口径（v2.1 不变）：**B 运行 = 计划审核 + 代码审查合计**（A2 合并后每包每轮省一次；复杂度审查只加小节不加环节、不额外计数）；修复循环 ≤3 轮/问题（质量裁决，非预算上限）。
- 研究员运行 ≤ 调研清单注明的批次上限（沿用 ≤5 并行分批）。

**场景2 技术调研储备（v2.1）**：预算台账**只统计不控制**（同修复包口径）——台账照建、固定块写「上限：只统计不控制（技术调研储备）；token 用量仅统计」，研究员每批派工点火即记一行（环节＝调研-批次N，含异常与中断），**不设 C/B/工作轮三项硬上限**；token 列照填；全程无费用概念。

### 4.2 任务包预算块（02_开发方案与任务包.md 固定格式）

调度员按基线填写，关卡2 前用户可见可改：

（无费用项：订阅制不按量付费；token 用量仅入台账统计，不作停机依据）

**修复包（TP-修复N）只统计不控制**：不填预算块上限，台账照记逐次运行与 token 用量，供用户自行管理；同一问题 >3 轮修复裁决机制保留。

| 时间 | 环节 | 模型 | 结论 | runId | attempt | 派工前阶段 | 结算后阶段 | candidateCommit | evidencePath | 累计C运行 | 累计B运行 | 累计工作轮 | token用量 |

| YYYY-MM-DD HH:MM | 计划审核 | B | 通过〔DONE〕 | — | 1 | 待启动 | 执行中 | — | — | 0 | 1 | 1 | — |

- **台账 schema v2（TP-B · D1）**：固定块增「账本身份」行（`账本身份：<taskId> | schemaVersion：2 | <repoRelativeTaskPath> | <flowType>`；身份与任务目录不符 = 拒绝派工，防串档）；明细增列 `runId / attempt / 派工前阶段 / 结算后阶段 / candidateCommit / evidencePath`；结算按**完整 runId 精确匹配**（无「第一条已派工行」回退；重复结算拒绝）。旧 v1 台账由 `dispatch_migrate` 一次性迁移（写回前备份 `预算台账-v1备份-YYYYMMDD.md`，不可解析行原样保留并标注；迁移演练在 `.tmp/` 副本上做）。
- **返回六态（TP-B · D3）**：子代理返回结果态六枚举 `DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED / FAILED / INTERRUPTED`——台账结论列中文摘要照旧 + 状态词映射记枚举（中断↔INTERRUPTED、失败↔FAILED、通过↔DONE/DONE_WITH_CONCERNS、其余同词）+ 记原因；DONE/DONE_WITH_CONCERNS 要求阶段合法前移，DONE_WITH_CONCERNS 另要求执行自测文档含「concerns」固定小节（缺失按证据缺失拒绝结算）；后四态「阶段不前移」是合法结算（计次 + 释锁 + 消息明示下一步），调度员按失败与中断路径处置。
- **恢复语义（TP-B · D4 · 账本四方一致）**：`dispatch_status` 做四方一致检查（账本身份行 vs `状态.md` 头〔当前阶段/候选commit〕 vs 证据文件存在性）并给**续跑建议**——已有「通过结论行」（结论列状态词为 DONE 或 DONE_WITH_CONCERNS 的结算行）的环节**不得重派**，指向第一个无结论环节；有「已派工」行且锁仍在 = 悬空（按失败与中断路径处理：清残留锁 + 台账补记结论）；无悬空行只剩锁 = 异常残留，清锁即可。

### 4.4 判定规则

- 调度员**每轮开工先读台账固定块对照预算块**：C/B 运行次数、工作轮为**硬上限**——任一超限 → **立即停止推进**（goal blocked）+ 非技术化决策简报（复用 >3 轮机制）→ 用户裁决。
- **token 用量仅统计参考**：任何用量水平都不构成停机依据（硬上限只看次数/轮数）。token 用量硬上限仅待第 3 层计量落地且口径可信后可选开启。
- **计次规则（派工即计次）**：凡 B/C 派工点火即计一次运行，**含异常返回与用户中断**；恢复轮对照工作证据（协同区三件/修复包两件）与 git log 对账补记漏记（中断条目照记「中断」）。
- token 用量列：第 3 层计量启用前填「—」；启用后按 provider 上报值填写（无上报时按 4 字符/token 估算并标注）；**token 计量不可用时退回纯次数台账**，流程不受影响。
- **全程无费用概念**：台账/预算块/规范相关表述不出现费用/价格折算；「不统计费用」类否定表述照抄允许。

### 4.5 快速通道与合并测试（v2.1.2 新增）

> 依据：`01-设计/跨项目复盘沉淀/04_产品设计方案-TP-D2-v1.0.md`（三项目「合并测试/快速通道」自发变体收敛为正式语义）。四形态分名分义，**禁止混用**（欠账≠归并；合并测试不产生欠账；直修严格限定边界）。

**四形态分名分义**：

| 形态 | 定义 | 欠账 |
|---|---|---|
| 快速通道 | 用户显式授权豁免指定 B 环节（计划审核/代码审查）；C 自测与取证不豁免 | **必有**（FT 编号＋复审义务） |
| 合并测试 | 多包各自走完全流程（B 足额实派），合并为一场人工测试 | 无（不省 B、不产生欠账） |
| 归并 | 审核员在 AC 核验中单包裁定「接受现在不测」 | 不构成欠账（须显式登记＋用户知情） |
| 直修 | 免流水线单点修复；仅限纯测试/文档/非产品代码，安全相关禁止 | 登记制（调度员独立复跑取证收口） |

**快速通道六要素**：

1. **触发**（判断驱动，不立查表）：调度员判断＋用户授权双键（考量：同质小改动连发／无安全·无数据迁移·无共享接口变更／预算压力／用户在场可即时授权）。
2. **授权四要素**：原话逐字转录／授权编号／**授权对象分列**（「流程环节」vs「机器校验动作」——绕过对象性质不同）／**失效边界**（批次授权须写明包清单＋上限条数＋失效点，禁止无边界「沿用」）。
3. **欠账登记**：任务级 `决策记录.md`「快速通道欠账」固定小节；编号 `FT-<包>-N` 唯一；字段＝豁免环节/授权编号/**复审重点（预写，延后消费）**/覆盖清单写死（包＋commit 范围）/状态枚举（未清偿·已清偿·失效回落）/核销回写位；**「转 X 消失则回落未清偿」**。
4. **集中复审双触发**：产品任务验收前欠账必须清零，**或**累计达授权上限条数即触发；审核员独立派工（不采信自测、逐 commit 读 diff）；复审后修改须审核员复看；台账记一行 B。
5. **幂等保护**：编号唯一＋状态枚举防重复登记/重复复审＋覆盖清单写死消除口径差。
6. **取证纪律**：**豁免 B 不豁免取证**——执行自测照常落盘（真实命令＋输出片段、非空壳自检、统计行可复算）。

**预算口径三句**：① 被豁免的 B 环节**计 0、不占该包 B 上限**，台账环节列内嵌记「快速通道-<授权编号>」（C 足额照记）；② 集中复审＝独立 B 派工记一行；③ 触顶时快速通道＝**决策简报第三选项**（方案一扩档／方案二快速通道欠账／方案三缩小范围），预写各选项落盘动作，**不得默认推荐跳过**——取舍权归用户当场风险判断；抬档入账三处（任务包 02 §九预算块＋台账上限行＋决策记录裁决条目）。

**待人工测试态纪律三件套**：该态下任何改动（含运维动作）＝**改动即欠账**登记；后续测试窗口**必复验**；临时形态（如 HTTP 直连）必须**写切回路径**。

**配套模板**：授权块见 `_任务模板/02_开发方案与任务包.md`（快速通道授权块可选节）；欠账小节见 `03-开发协同/决策记录.md`；核销清单段见 `04-测试/验收结论.md`；台账记法见 `03-开发协同/预算台账.md`。

### 4.6 开发准备记录与开工门禁（v2.1.4 新增）

> 依据：`01-设计/首次使用引导/04_产品设计方案.md` v0.3 §二/§四/§五；用户 2026-10-08 裁定简化为「首次对话直接告知＋`enter_auto_mode` 单点机器门禁」。

- **三段式**：① **首次对话引导**——新会话首条消息调度员做秒级只读探查，有缺项或未验证项才输出针对性准备信息（零副作用：不安装、不改配置、不拉代码、不连远程）；② **按需补齐**——用户指定补哪项，调度员列动作与影响、取得授权后逐项执行；③ **开工门禁**——`enter_auto_mode` 在预算台账机器保险丝之后核对开发准备记录，**fail-closed 拒绝并列缺项**，无流程类型豁免（校验链见 §11.1 启动条件）。
- **记录载体（唯一）**：`00-项目管理/开发准备.md`（模板 `spec/templates/00-项目管理/开发准备.md`）；顶部固定块五字段＝`规范版本` / `必要项` / `未通过项` / `最近复查` / `门禁结论`；正文＝必要项清单表（编号｜层级｜条件｜执行位置｜必要性依据｜状态｜证据与日期｜缺项与建议动作）。
- **放行判定**：文件存在 ∧ 固定块可解析 ∧ 五字段齐备 ∧ `必要项` ≥1 ∧ `未通过项` = 0 ∧ `最近复查` 为日期形态 `YYYY-MM-DD`。任一不满足即拒绝并点名缺口与文件路径。
- **状态词四枚举**：`已验证`（现场实测，附证据与日期）/ `用户确认`（用户裁决类信息，探查无法重建：执行位置 / 远程仓库 / 测试服务器连接 / codegraph 降级裁定）/ `未验证`（未核实或已过期）/ `不适用`（**须写理由**）。`门禁结论` 字段为最近一次复查结果的人读留痕，**机器不消费其值**（机器只看必要项/未通过项/最近复查）。
- **边界与旁路**：记录不含密钥/私钥/token/完整敏感连接串；探查本身不持久化（每个新会话重新探查，成本秒级、天然幂等）。绕过 `enter_auto_mode` 直接派开发员属**流程违反**，由 persona 纪律约束，不新增机器拦截面，如实声明不宣称完全强制。

## 五、任务包串行

1. **任务包打包策略**：适合一起开发的功能打成一个包（内聚模块/页面组）。无法合并的多包按依赖排序**串行推进**：一次只开发一个包，该包 04-测试 验收结论落盘（状态 已完成）后才激活下一包。
2. **切分标准（v2.1 唯一标准）**：**能否构成一次有意义的人工测试**——两次人工测试之间的任务包切分没有意义（用户不会因为包切细而多测一轮），应打成同一批全自动连跑。
3. **授权范围（A1 一次授权多包连跑；#33：授权节点＝设计定稿确认）**：**设计确认即开发授权**——用户在关卡1 选择「确认即开工」后，任务包生成完成即由调度员自动核查首包前置 → 激活首包（置 `待审核`）→ `enter_auto_mode`（视为已获授权），此后：
   - **两次人工测试之间的所有任务包全自动连跑**，包间无人工关卡（状态置 `待审核` 由调度员机械完成，不再要口头授权）；
   - **每次人工测试通过 = 放行信号**：自动核查下一包前置（02 标注的依赖前置全部 `已完成`）→ 置 `待审核` → `enter_auto_mode` 继续推进；
   - **异常硬停**：驳回 >3 轮 / 范围漂移 / 预算触顶 → 立即停机上报，等用户裁决；
   - 用户**可随时喊停**（对话里一句「停」即打断）。
4. **人工介入点（收敛为四处）**（#33 授权合并后口径）：设计定稿确认（关卡1，含分流「确认即开工 / 仅定稿存档」与 #32 提示）＋ **各次人工测试**＋ 异常停机裁决＋ 收尾授权（关卡3）。除此之外不再有人工关卡——「开始自动推进」（关卡2）在「确认即开工」下由调度员机械执行、不构成人工关卡。
5. **初始态与激活**：任务包生成时全部包初始 `待启动`；激活 = 调度员核查前置包（02 中标注的依赖前置）已全部 `已完成` 后，将当前包状态置 `待审核`（「确认即开工」下由调度员在任务包生成完成后机械执行，无须用户再开口）。
6. **goal 粒度 = 单包**：`enter_auto_mode` 仅做单包校验（单包串行铁则仍在机器层执行）；系统内不存在一包未通过人工测试（验收结论落盘）即开发下一包的路径——连跑实现方式=每包到达 `待人工测试` 硬停、测试通过后由调度员**再次调用 `enter_auto_mode` 为新包建 goal**，而非一个 goal 跨包。
7. **多包识别提示**：调度员开工/恢复时扫描各包状态，本包 已完成 且存在 待启动 包 → 按第 3 条自动核查前置并放行（无需用户重复授权）；前置未满足时对话提示用户。

## 六、验收阶段协议（修复循环与收尾）

1. **发测试**：调度员把待测试功能说明（测试入口、功能点、预期表现、已知限制）随构建产物发用户，状态 `待人工测试`；测试入口说明随安装包走（05-交付/安装包/版本号目录）。
2. **报问题**：用户对话直接描述问题；调度员确认（复现路径、期望 vs 实际）并分级：**修复级**→修复循环；**任务级**→升级开发阶段全流程（计划审核 → 执行 → 待审查，同 5 态）；**需求级**→回设计阶段，声明定稿版本失效。用户每轮实测记录落 `04-测试/<TP>/测试记录-YYYYMMDD.md`。
3. **修复循环（含审核员）**：调度员生成修复任务包（`任务包/TP-修复N/`）→ 派开发员修复（自测+候选 commit，修复 diff 最小化）→ **审核员修复代码审查**（含 AC 证据核验 + 复杂度小节；驳回回修复中）→ 调度员检查（复核**证据齐备性**，有问题退回重改；判断权归审核员）→ 构建/更新 → 再次提交用户测试。修复包每次派工记入 `预算台账.md`（只统计、不设上限）。
4. **本包关闭**：用户确认本包通过后，调度员写 `04-测试/<TP>/验收结论.md`（含**债务清单**段），状态置 `已完成`。
5. **串行衔接（v2.1 连跑）**：存在下一包时，**用户实测通过本身即放行信号** → 调度员核查其 02 标注的依赖前置包全部 `已完成` → 将该包状态 `待启动→待审核` → 直接 `enter_auto_mode`（**不再要求用户重复说「开始自动推进」**；首包在「确认即开工」下由调度员在任务包生成完成后机械开工，见表 §七）。
6. **收尾（最后一包）**：用户确认通过并明确指令后，调度员按序执行：① 更新服务器（按项目既定部署方式；无目标服务器则跳过并记录）；② push git 远程仓库（失败或远程有变更→暂停报告，不自行 pull/merge/rebase）；③ 更新文档（README/操作手册/设计文档版本）+ **ponytail-debt 扫描**（汇总 `ponytail:` 注释，标注无升级路径的腐烂风险）；④ 产品级收尾记录并入最后一包 `04-测试/<TP>/验收结论.md`，状态 `已完成`，关闭产品任务。相关记录落 `05-交付/<TP>/` 任务级三件（构建记录-/推送记录-/部署记录-YYYYMMDD.md）——v2.1 交付区新增。

## 七、验收硬规则与人工关卡

**人工关卡：**

| 关卡 | 时机 | 用户确认内容 | 未通过去向 |
|---|---|---|---|
| 关卡1 · 设计确认**（＝开发授权 · #33 授权合并）** | 04 方案 + 原型提交后（**场景1 提交物差异**：现状确认记录 + 04 方案 + 06 定稿记录；短链豁免原型与 05 分模块设计） | **设计确认即开发授权**——确认时给分流选择：**「确认即开工」/「仅定稿存档」**；同场展示 #32 模型配置提示（三角色钉模型 + reasoningEffort + 主会话模型；要改则**从下一会话生效**）。产品范围、核心流程、功能与规则、原型页面与关键状态；确认后写 06 定稿记录（固定块锁定版本号） | 按回退表逐级回退 |
| 关卡2 · 首包自动开工（**机械动作，非人工关卡** · #33） | 任务包生成完成后（已选「确认即开工」） | 无须用户再开口：调度员自动核查首包前置 → 激活首包（置 `待审核`）→ `enter_auto_mode`（**视为已获授权**）。**一次授权多包连跑**（**授权节点＝设计确认** · #33 授权合并；切分标准=能否构成一次有意义的人工测试；两次人工测试之间全自动连跑；测过自动放行后续包；异常硬停；用户可随时喊停）；旧的**一包一授权**模型已在 v2.1 A1 取消 | 选「仅定稿存档」或中途改主意 → 停在 `待启动` 等你发话 |
| 关卡3 · 收尾授权 | **最后一包**用户测试通过后 | 用户确认「测试通过」并明确指令收尾；push 失败或远程有变更时暂停报告 | 继续修复循环 |

> **授权节点说明（#33 授权合并）**：关卡2 并入关卡1 的依据是**授权必须锚在用户能做有意义判断的节点**——目标用户无代码能力、无法审核任务包，而设计定稿是他能判断的最后一站。因此「确认即开工」下的首包开工是**平台惯例动作**，不再是独立人工关卡；各次人工测试、异常停机裁决、收尾授权（关卡3）与 push 门禁**全部不变**。

> **v2.1 · #33 修订前的旧口径（保留备查、不再执行）**：`| 关卡2 · 开发授权 | 每个任务包齐备并激活后 | 用户明确说「开始自动推进」；设计确认 ≠ 开发授权；一包一授权 | 不启动，继续对话 |`——「设计确认 ≠ 开发授权」与「一包一授权」均随 #33 授权合并、v2.1 A1 连跑作废；现行口径见上表两行。

**条件关卡 · 审核员可行性复核**（任一成立即触发）：改造既有系统核心流程；复杂权限/敏感数据/数据迁移；多外部系统或不稳定接口；架构替换/核心依赖升级/部署方式变化；高成本或高失败代价。审核员只写复核报告（落协同区 `计划评审-vX.Y.md`），问题退回调度员。

> **场景1 默认触发（v2.1）**：「改造既有系统核心流程」对场景1 天然成立 → **默认触发**可行性复核（审核员输入＝02 系统现状分析 + 04 方案）；**短链小改可在档位选择时豁免**，豁免记录入 06 决策清点段。

**验收硬规则：**
- **无证或不可证伪驳回**：自测/验证结论只写"通过"无真实命令输出 → 直接驳回；回归证据**不可证伪**（典型：修复前后都通过的"假 RED"，失败并非因目标缺陷发生）→ 同样驳回；
- **不可自动化例外**：回归用例确实无法自动化执行时，记录不可自动化原因 + 修复前人工/可观察失败证据 + 修复后同路径证据，**充分性判断权归审核员**；
- 修复后必经审核员代码审查；同一环节 >3 轮出决策简报；
- **验收结论（含债务清单）落盘后才允许 已完成**；收尾必须用户明确授权；
- push 必须用户明确指令，失败或远程有变更时暂停报告，不自行 pull/merge/rebase。

## 八、ponytail 规则（最小实现纪律）

- **六档阶梯**（开发员写代码时逐级停靠，第一档适用即止）：需求不存在（YAGNI）→ 标准库 → 平台原生 → 已装依赖 → 一行代码 → 最小实现。
- **`ponytail:` 注释约定**：故意简化处写 `ponytail:` 注释，说明天花板与升级路径（如 `# ponytail: 全局锁，吞吐成问题再换每账号锁`）。
- **最小可运行检查**：非平凡逻辑（分支/循环/解析/安全性路径）留下**一个**最小可运行检查（assert 式 `demo()`/`__main__` 自检或一个小测试），随自测证据提交；平凡一行代码不需要测试。
- **复杂度审查小节**：审核员代码审查与修复审查各含一个「复杂度发现」小节（delete/stdlib/native/yagni/shrink 五标签 + net 行数结论）；**只加小节不加环节，不占额外 B 运行次数**（预算块不动）。
- **收尾债务清单**：收尾时 ponytail-debt 扫描 `ponytail:` 注释 → 债务清单写入验收结论.md；标注无升级路径的腐烂风险。
- **边界**：校验/安全/可访问性/显式需求**绝不偷懒**（When NOT to be lazy）；调度员/研究员不加载 ponytail；ponytail 不砍流程自身（YAGNI 面向 02-代码/ 产品代码，三阶段五区是个人使用的控制面，不反向瘦身）。

## 九、设计决策清点协议（grill-me）

> **机制说明**：本协议由调度员 persona 注入实现（注册期生效），**不直接加载外部 skill**——与 ponytail 融合方式一致。skill 不在会话技能目录，运行时加载不可依赖。

**定位**：04 方案（含 05 分模块设计）产出后、原型制作前的交互态子步骤；高风险任务在可行性复核通过后执行。不新增状态机状态；用户可随时说「跳过」。

**三档（用户选，v2.1：开场先问档位）**：

> **开场动作（决策#23，v2.1）**：决策清点开始前**先问用户档位**（跳过 / 轻量 / 标准）——能力保留、成本用户自控；**缺省不再固定「标准」**（用户不表态时按任务档位默认：新产品任务标准、**短链任务默认轻量**）。档位选择记入 06 决策清点段。

- **跳过**：用户直接进入原型/关卡1；
- **轻量**：只清零 01「待确认问题」+ 04「风险与待决策事项」两个清单；
- **标准**：完整决策树覆盖（顶层 3~6 分支 + 各分支子决策）。

**协议六条**：

1. 先列出顶层决策分支（3~6 条），**最基础的先问**（其余分支常依赖它）；
2. 逐分支问到底、子决策按依赖顺序；分支清零再进下一分支；
3. **每问先给推荐答案再问用户**，等用户回答再继续；
4. **能自查的不问**：调研报告、现有代码（codegraph）、05 分模块设计能回答的，自查解决并记录依据；
5. 停止条件：全部分支解决、无「it depends」；未解决项显式列入 06「未清零项」并标注依赖与阻塞；
6. 敲定的决策**实时写入 决策记录.md**（grill-with-docs 落盘纪律），会话结束时汇总进 06 决策清点段。

**边界**：决策清点是**产品决策对话**（调度员⇄用户）；技术可行性归审核员 B 复核——grill 不替 B 问技术细节，B 不替用户做产品取舍。

**回退重跑（与第三节回退表衔接）**：需求级问题回退设计阶段时，重跑受影响分支的决策清点，**已清零分支保留**。

**中断恢复**：交互态随时续问；已清零分支已写入 决策记录.md 即持久，无需重来。

**输入清单**：01「待确认问题」与 04「风险与待决策事项」是决策清点的输入清单，进入决策清点时逐条清零（每问先给推荐答案），不再停留在"记着以后再问"的被动状态。

## 十一、文档惯例

### 11.1 状态文档

`状态.md` 每次阶段变更时更新，**顶部固定格式块**（唯一机器解析源，自动推进模式只解析该块；正文其余供人读）：

```text
当前阶段：执行中
当前环节负责方：模型C
任务类型：大任务
流程类型：产品设计全流程        （或「仅开发」，缺省仅开发；v2.1 增「技术调研储备」——场景2 专用）
设计目录：01-设计/<产品任务>/任务包/<TP编号>-<名>   （仅开发任务可缺省）
本环节驳回轮次：0
候选commit：（C 形成候选 commit 后填写）
下一步：C 按任务包执行并自测
必读文件：01-设计/.../任务包/TP/02_开发方案与任务包.md
最近更新：YYYY-MM-DD HH:MM
阻塞/待办：（如有）
```

- **本环节驳回轮次**：阶段前移到新环节时由写状态方清零；同一环节每驳回一次 +1。
- **候选commit**：C 每次形成新候选 commit 后更新；验证、审查、测试必须针对同一个候选 commit。
- **预算记账**：状态头**不设**预算计数字段——预算记账载体 = 预算台账.md（第四节）。
- **写盘纪律**：先写产出文档，最后更新状态.md；落盘用"写临时文件 + 强制移动"（Windows 用 `Move-Item -Force` 等价物，rename 不能覆盖已存在文件）。

### 11.2 交接块（每份任务包文档顶部固定）

```text
【交接块】
目标：一句话（本环节在做什么）
上一环节：A 已产出任务包 / B 已审核通过……
本环节要做的：一句话
关键输入文件：02_开发方案与任务包.md
上一环节已确认：验收标准可测试
未决问题：（如无写"无"）
下一步负责人：模型C
```

- 文档主体是"证据与记录"，交接块是"指令"，两者分开。
- 每个阶段完成时，负责模型必须在交接块写清：下一步谁做、做什么、读哪些文件、有什么坑。

### 11.3 决策记录

`决策记录.md` 仅追加四类条目（普通驳回不记录）：

```text
### YYYY-MM-DD HH:MM | 类型（变更/分歧/例外/裁决）
参与方：
背景：
各方意见/选项：
结论与理由：
```

### 11.4 工作证据文档（协同区，v2.1 扁平化 + 三件）

- 模型间审核意见与工作证据按 **三件**落盘，**直接放任务根**（v2.1 取消 `过程记录/` 子目录）：
  - `计划评审-vX.Y.md`（审核员：计划审核 / 可行性复核；每轮另存新版本 v0.1→v0.2…，驳回链全程留痕、不覆盖）；
  - `执行自测-YYYYMMDD.md`（开发员：改动清单 + 自测证据 + 六档自审声明；**同日多轮用 `-YYYYMMDD-N` 后缀，N 从 2 起**）；
  - `代码审查-vX.Y.md`（审核员：**AC 证据核验（无证驳回）+ 代码审查（含复杂度发现小节）一次完成**；每轮另存新版本）。
- **取消**：`03_验证审核.md`（并入代码审查，A2）；`项目进度基线.md`（职责并入 `00-项目管理/当前状态.md`）；`06_构建更新记录.md` 移至 `05-交付/<TP>/构建记录-YYYYMMDD.md`。
- **修复包**（`<TP-修复N>/`）：加「修复」前缀——`修复执行自测-YYYYMMDD.md` / `修复代码审查-vX.Y.md`（规则同主包）。
- 审核意见文档内容：通过/驳回结论 + 原因；驳回时按"已检查的影响范围 / 采用的检查方法 / 已执行的测试 / 未覆盖的区域 / 剩余风险"五要素记录，并声明失效结论与重审起点。
- 普通交接（阶段正常前移）不建文档，只更新 `状态.md` 与各文档交接块。
- ★命名沿革说明（**不再沿用**）：v2.0 的 `过程记录/01_计划审核.md`、`过程记录/02_执行与自测记录.md`、`过程记录/04_代码审查.md` 与 v1.1 的「开发计划/01~05」+「协同文档/」命名均已作废；旧项目在途包按旧名继续走完，新包一律用 v2.1 三件。

### 11.5 06 设计定稿记录固定块与决策清点段

06 顶部为状态.md 同款固定格式块（供 enter_auto_mode 机器解析）：

```text
---
文档：06_设计定稿记录
确认版本：vX.Y
确认日期：YYYY-MM-DD
设计目录：01-设计/<产品任务>
---
```

正文：已确认页面与流程；**决策清点段**（每分支：问题/推荐答案/最终决定/依据；未清零项清单——含依赖与阻塞；附一行机制说明：本协议由调度员 persona 注入实现、不直接加载外部 skill）；需修改内容；暂缓项；原型无法表达但开发必须实现的规则；自检附录。定稿后不得静默修改 04/05/原型；变更须升版本并在 06 声明失效范围。

### 11.6 版本规则与修订记录

- 任务包 01/02 **豁免版本递增**：原地修订 + 文末修订记录（日期+改动摘要+触发环节）；04/05/原型/06 适用「不覆盖、版本递增」（另存新版本号文件，原版本保留）。
- 每次构建产物放 `05-交付/安装包/<名>-v<版本>/`（目录 + zip），附测试入口说明。

### 11.7 项目看板维护规则

项目根目录的 `项目看板.md` = **项目级任务总览**（人读导航层），形态：

- **三区**：✅已完成 / 🔄进行中 / 📋待办，各含任务编号 + 内容 + 状态链接（定位到 `03-开发协同/<任务>/状态.md`）；
- **维护方**：调度员；更新时机 = 任务立项 / 阶段大迁移 / 验收关闭 / 裁决入账后；
- **与协同区 `任务看板.md` 分工**：项目看板 = 项目级人读导航（根目录，面向用户）；任务看板 = 协同区任务状态同步（面向流程）；两者都链接到任务目录；
- **权威性**：冲突以各任务 `状态.md` 为权威；
- 项目根缺失 `项目看板.md` 时，由调度员按模板集第十节 `项目看板.md` 模板补建。

## 十二、部署纪律

- 验收阶段「更新服务器」优先走**项目内部署脚本**（shell 执行）；**预设默认不挂部署工具**（如 ssh）。
- 需远程部署时按项目实施期决策挂载 ssh 类工具；**无部署目标时跳过并记录**（收尾清单中写「待人工执行」或跳过说明）。
- 部署通道不可用时：完成构建与 push，更新服务器步骤标记「待人工执行」并给出操作清单。

## 十四、场景扩展（v2.1 新增）

### 14.1 场景1 · 修改已有系统功能/bug

**定位**：设计阶段**前置变体**——现状研究替代同类产品调研，需求确认后汇入现有主流程（方案→定稿→任务包→自动推进→人工测试）。**开发 5 态、修复循环 5 态、关卡语义、候选 commit 纪律全部不变。**

**开工判定与脚手架补建（保险丝三分支）**：

| 探测结果 | 分支 |
|---|---|
| 项目根有 v2.x 规范 | 现行主流程（含五区项目内改 `02-代码/` 子系统——本场景不覆盖，维持现状） |
| 项目根无规范、且为空白/新项目 | 现行脚手架初始化（复制规范 + 模板） |
| 项目根无规范、但存在**既有代码系统**（有源码目录/依赖清单/构建配置任一） | **场景1 分支**：① 向用户确认进入「修改已有系统」模式；② 补建脚手架（规范 + 模板按 v2.1 六区结构落位）；③ codegraph 索引建于**项目根**；④ 无 `.git` 时提示用户，确认后**代为 `git init` + 首次 commit**（`.gitignore` 含 `.codegraph/`、`.tmp/`、依赖目录）——git 是候选 commit/核查/版本绑定的地基 |

脚手架补建**不搬运、不改造**既有代码；六区目录与老系统源码目录**并列存在**。

**设计链（新增子状态「现状研究中」+ 规模档位）**：

```text
需求沟通中（录入修改意向 → 01_需求说明文档.md，标注设计链档位）
→ 现状研究中【新状态】（研究员+codegraph → 02_系统现状分析.md；用户确认现状）
→ 方案设计中（短链=轻量版；标准链=完整版+05 分模块）
→ 待可行性复核（默认触发，短链可豁免）
→ 设计决策清点（短链默认轻量档）
→ 原型制作中（短链豁免；标准链照常）
→ 待设计确认 → 方案已定稿 → 任务包生成中 →（开发阶段不变）
```

- **档位**：立项时用户在 01 需求说明标注「设计链档位：短链/标准」；短链最小产物集与豁免范围见 §3.1b。
- **现状确认**：研究员报告提交后用户对话确认（非正式关卡，同类调研清单确认规格），确认记录写入 01 修订记录，状态前移。
- **批次边界**：默认一轮一份；系统过大（研究员自报一轮覆盖不全，或 codegraph 模块数明显超单报告容量）时调度员按模块切分批，每批一份（`02_系统现状分析-<模块组>.md`），用户逐批确认继续。
- **可行性复核默认触发**：见 §七条件关卡注（短链可豁免，豁免记录入 06 决策清点段）。

**《系统现状分析》模板契约（`01-设计/02_系统现状分析.md`，六节）**：

1. **系统概览**：技术栈/入口/构建方式/模块图谱（codegraph 概览：包/模块/符号规模）；
2. **关键调用链与数据流**（与修改意向相关的链路，附 codegraph 查询证据）；
3. **修改意向相关现状详查**（现状行为是什么、问题点/扩展点在哪）；
4. **影响面初判**（`impact`/`callers` 证据：改动可能波及的模块清单）；
5. **事实/推断标注与未解决问题**；
6. **安全纪律声明**（只读静态分析，未执行脚本/未起服务/未改文件；codegraph 不可用时注明「未使用 codegraph」并按降级口径以全文搜索+git 分析替代）。

**研究员派工·现状研究变体**（自包含契约）：必读 01 需求说明 + 会话开始 `codegraph sync`；必写 02_系统现状分析.md（照抄上述六节契约）；只读纪律与注入免疫声明沿用；返回格式不变（结论一句话 + 报告路径 + 未解决问题）。

**目标代码区**：见 §一「目标代码区（v2.1）」——现状确认时用户圈定源码目录集合，记入 01/02/06，状态头不加新字段；单一写入者规则、B 环节 `git status --porcelain` 核查范围、无关改动不得提交，全部跟随目标代码区。

**任务包影响面约束**：`_任务模板/02_开发方案与任务包.md` 第十节「现状引用与影响面约束（场景1 必填，新产品任务写"不适用"）」——引用 `02_系统现状分析.md` 版本与相关节；列出**影响面清单**（允许改动的模块/文件集合，取自现状分析第四节）；**越界＝范围漂移，立即停工写决策记录（例外类）上报**。

**开发/验收阶段**：不变——转移表、候选 commit 绑定、无证驳回、ponytail、预算分档、修复循环、收尾与 push 门禁全部照旧。

### 14.2 场景2 · 技术调研储备搜索

**定位**：**独立终态流程**——不建 goal、不进入开发阶段、**不存在从调研报告自动生成任务包的路径**。全程交互态由调度员推进（研究员派工为后台并行，同设计阶段调研规格）。调研结论要落地实施时，用户**另立产品任务**走主流程（主流程的同类产品调研可直接引用本流程产物）。

**状态链**：`方向确认中【新状态】→ 清单待确认【新状态】→ 调研中（复用）→ 已完成（复用）`（转移表见 §3.1b）。

**双区落盘**：

- 协同区：`03-开发协同/TR<编号>-<主题>/` = `状态.md`（流程类型：**技术调研储备**；设计目录指 `01-设计/技术调研/<主题>`）＋ `预算台账.md`（**只统计不控制**）＋ `决策记录.md`；
- 设计区：`01-设计/技术调研/<主题>/` = `01_调研方向确认.md`（业务需求与场景/用户直接给出的技术路线或工具/边界与脱敏注意）、`02_调研清单.md`（复用泛化后的调研清单模板）、`03_调研报告/<对象>.md ×N`、`04_调研汇总报告.md`（对比矩阵汇总 + 分场景推荐 + 未解决问题 + 各对象报告索引）；
- `01-设计/技术调研/` 为设计区**保留子目录**（§2.1「01-设计 内部结构按项目实际定」框架内，v2.1 目录树显式登记）。

**调研清单与逐批拓展机制**：

1. **方向确认**：用户描述业务需求/场景，或直接给出技术路线/工具；调度员落 `01_调研方向确认.md`（含搜索词脱敏检查）。
2. **清单**：调度员拟 `02_调研清单.md`（首批对象＋每项重点关注点＋批次号）→ 用户确认/增删 → 调研中。
3. **并行调研**：研究员并行 ≤5、超出分批（现行限制沿用）；每对象一份报告。
4. **拓展**：研究员调研主对象时同步检索同类方法/工具/方案，候选写入报告「同类拓展候选」小节（每条一句话 + 链接 + 与本主题相关性）。
5. **逐批推进（不设固定上限）**：每批返回后调度员校验齐备性、汇总各报告拓展候选并去重，向用户**建议下一批清单（含建议规模与理由）**；用户确认/增删/喊停后才派下一批，批次号递增入 02 清单。用户随时可宣布进入汇总。
6. **汇总**：调度员写 `04_调研汇总报告.md` 并**当面向用户汇报**（要点 + 推荐 + 未解决问题），状态 → 已完成。

**报告模板增节**（`03_调研报告/调研报告模板.md`，场景2 必填、产品调研选填）：

- **技术路线对比矩阵**：维度＝适用场景/成熟度/社区与维护/License 与复用风险/接入成本/与本主题契合度；
- **同类拓展候选**：拓展发现的方法/工具/方案清单（一句话 + 链接 + 相关性），供调度员汇总成下一批建议。

**裁决门槛（v2.1.3 · TP2，可退回条款；不新增状态/环节/角色）**：

- **清单裁决列**：`02_调研清单.md` 调研对象表增「裁决」列——go / needs-clarification / kill（场景2 必填；needs-clarification＝带澄清问题按对象退回重派，kill＝说理后排除；场景·新产品开发写「—」）；
- **汇总三态裁决段**：`04_调研汇总报告.md` 增批次裁决段——每对象 go / needs-clarification / kill 三态一行、附一句话依据；needs-clarification/kill 按对象退回重派或排除；
- **反证强制小节**：04 汇总报告含「反证强制小节」（不得省略）——每条推荐至少一条已查反证及结果，找不到反证须显式写「未找到」及检索范围；**反证小节缺失即按对象退回重派**；
- **ASSUMPTION 标注**：任何无来源支撑的主张一律标 `ASSUMPTION` 并在「未解决问题」表登记核实路径；**评级判据自定，不给量化假装精确**。

**预算口径**：**只统计不控制**（同修复包）——见 §4.1 末段。

**入口与触发**：**意图关键词＋复述确认**——用户表达「技术调研/调研储备/摸底某技术方向」类意图时调度员进入本流程，进入前复述「主题 + 形态（独立调研，不进开发）」请用户确认；开工判定**不做**环境自动探测（避免误触发）。

**封闭性声明**：本流程**无任何「自动进入开发」路径**；不产生任务包、不建 goal、不受任务包串行铁则约束（与在跑任务包可并行存在，因其不占开发流水线）。
