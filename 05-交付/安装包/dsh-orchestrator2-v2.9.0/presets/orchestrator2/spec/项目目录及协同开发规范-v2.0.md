# 项目目录及协同开发规范 v2.0

> 适用场景：FDE 工程师（无代码能力）通过多 AI 协同完成新项目从需求到交付的全过程。
> 本文 = 新项目标准目录结构（五区）+ 多智能体协同开发规范（三阶段全流程）。
> 每个新项目开工时：① 按第二节建好目录骨架（可先建空目录）；② 将本文件复制到 `03-开发协同/` 下作为项目内规范；③ 从模板集（第十节模板索引）复制所需模板落位。
> v2.0 变更（相对 v1.1）：五区目录体系（新增 04-测试）；角色表新增研究员；三阶段状态机（设计阶段 9 态 + 开发阶段 7 态 + 验收修复循环 5 态 + 收尾）；任务包双区同名对应（设计区任务包 + 协同区状态/证据；状态头 `设计目录` 机器指针）；预算体系（预算基线 + 任务包预算块 + 预算台账）；任务包串行（一包一授权）；验收修复循环含审核员代码审查；设计决策清点协议；`_任务模板/` 双区模板；过程记录 01~04 命名体系；安装包版本号目录管理。原有开发纪律（单一代码写入者、候选 commit、.lock、git status 核查等）原文保留，仅换称谓。

## 一、角色定义

| 模型 | 角色 | 职责 |
|------|------|------|
| 用户 | — | 聊需求、确认设计、授权开发（一包一授权）、人工测试、确认验收、授权收尾；全部人工关卡最终决定权 |
| 模型A | 调度员 | 需求沟通、搜索调研清单、派发研究员、汇总学习、产品设计、HTML 原型、任务包、验证、检查修复、构建/更新、收尾。**永不修改 `02-代码/`** |
| 模型R | 研究员 | 按派工调研单个（或一组）同类产品：功能、设计思路、公开代码与 License，各出一份报告。只读研究；不执行外部代码；不改项目文件 |
| 模型B | 审核员 | 高风险设计可行性复核（条件触发）；计划审核；代码审查（含复杂度审查小节）；修复代码审查。只读审核，不改方案/原型/代码 |
| 模型C | 开发员 | 按任务包开发、自测（附真实命令输出）、候选 commit；验收阶段修复开发。`02-代码/` 唯一默认写入者，按六档阶梯写最小实现 + `ponytail:` 注释约定 |

**单一代码写入者规则（不变）：**
1. 同一时刻只有一个角色可修改产品代码；默认只有模型C能改。
2. A、B 审核时只读代码，发现问题写明退回 C，禁止审核时顺手修复。
3. 各模型开始工作前必须检查 `git status`、当前分支和基线 commit。
4. 不得覆盖、删除或提交与本任务无关的改动。

**模型钉选纪律：** 任何钉选模型 ID 实施前必须核实（本机 provider 目录/配置）；核实不存在或无凭证立即回报用户选替代，不得静默换模型。`max` 等推理等级（reasoningEffort）不属于模型 ID 的一部分。

## 二、目录体系（五区）

### 2.1 五区语义

| 目录 | 语义 | 内容性质 | 变化频率 |
|---|---|---|---|
| `01-设计/` | 要做什么的**定义**：需求→调研→总体设计→分模块设计→定稿→任务包→原型 | 版本化产物（适用"不覆盖、版本递增"规则，任务包文档豁免） | 低 |
| `02-代码/` | 产品本体，唯一代码区，codegraph 管理 | 代码 | 开发员写 |
| `03-开发协同/` | **状态机 + 模型间工作证据**（审核结论、执行自测、验证、决策、预算台账） | 高变化操作记录 | 高 |
| `04-测试/` | **用户测试出的内容**：测试记录、问题清单、验收结论 + 过程材料（自交付移入） | 实测证据 | 验收期高 |
| `05-交付/` | 面向客户的交付物：安装包（版本号目录 + zip，附测试入口说明）、操作手册、演示方案、宣传材料 | 交付物 | 构建时 |

### 2.2 完整目录树

```text
项目名称/
├── 项目看板.md                          ← 项目级任务总览（调度员维护；各任务权威状态以 状态.md 为准）
├── 01-设计/
│   └── <产品任务>/                      ← 一个产品/需求一个目录
│       ├── 01_需求说明文档.md            ← 调度员（需求沟通中）
│       ├── 02_同类产品调研清单.md         ← 调度员（同类产品搜索中）
│       ├── 03_调研报告/<产品>.md ×N      ← 研究员×N（调研中，每产品一份）
│       ├── 04_产品设计方案.md            ← 调度员：总体/主题功能设计（头带 vX.Y）
│       ├── 05_分模块设计/<模块>.md        ← 按需：分模块/功能的细化设计
│       ├── 06_设计定稿记录.md            ← 关卡1 结论 + 顶部固定块（确认版本）+ 自检附录
│       ├── 原型/index.html + assets/    ← 调度员（设计资产，非生产代码）
│       └── 任务包/<TP编号>-<名>/          ← ★ 一包一目录（文档豁免版本递增）
│           ├── 01_需求分析.md
│           └── 02_开发方案与任务包.md     （含追踪矩阵 + 设计版本引用 + 预算块 + 依赖前置标注）
│
├── 02-代码/                            ← 不变：唯一代码区
│
├── 03-开发协同/                         ← ★ 状态机 + 模型间工作证据
│   ├── 项目目录及协同开发规范.md          ← 本文件（复制至此，项目内版本优先）
│   ├── 项目进度基线.md
│   ├── 任务看板.md
│   ├── 预算基线.md                     ← 默认预算档（用户维护；缺失时按本规范内置默认档；不含价格）
│   ├── _任务模板/                      ← 双区模板（协同区目录 + 设计区任务包骨架，含预算台账模板）
│   └── <TP编号>-<名>/                  ← 与设计区任务包同名对应
│       ├── 状态.md                     ← 唯一机器状态源（初始 待启动）
│       ├── 预算台账.md                 ← 固定块（硬上限三项+累计）+ 逐次运行明细（派工即计次，token 用量可获取时填）
│       ├── 决策记录.md
│       └── 过程记录/
│           ├── 01_计划审核.md            ← 审核员 → 调度员
│           ├── 02_执行与自测记录.md       ← 开发员 → 调度员/审核员
│           ├── 03_验证审核.md           ← 调度员
│           └── 04_代码审查.md           ← 审核员（含复杂度发现小节）
│
├── 04-测试/                            ← 用户实测区
│   └── <TP编号>-<名>/
│       ├── 过程材料/                    ← 测试脚本、测试数据、冒烟/检查记录（可选）
│       ├── 测试记录-YYYYMMDD.md          ← 用户实测：功能点/结果/问题（现象/期望/复现路径）
│       └── 验收结论.md                  ← 本包通过结论 + 债务清单段；最后一包含产品级收尾记录
│
├── 05-交付/
│   ├── 安装包/<名>-v<版本>/ + zip       ← 每次构建产出版本号目录（附测试入口说明）
│   ├── 操作手册/
│   ├── 演示方案/
│   └── 宣传材料/
│
└── 历史记录/（可选，规则不变：原样归档、不改造、不作协同依据）
```

### 2.3 双区同名对应规则

- 任务包是**设计产物**（调度员设计、审核员审核的依据），落 `01-设计/<产品任务>/任务包/<TP编号>-<名>/`；
- 该任务包的**状态与过程证据**落 `03-开发协同/<TP编号>-<名>/`，同名同编号；
- 机器链接：`状态.md` 固定头含 `设计目录：01-设计/<产品任务>/任务包/<TP编号>-<名>`，`enter_auto_mode` 顺指针校验任务包文档，不靠人记；
- 切线语义：任务包 01/02 是"开发前"的设计产物 → 设计区；过程记录是"开发中"的工作证据 → 协同区。**切线正好落在开发授权关卡上**；
- "不覆盖、版本递增"规则适用 `01-设计/` 的 04/05/原型/06；**任务包 01/02 豁免**（待修订循环需反复修改）——原地修订并在文末附修订记录（日期+改动摘要+触发环节）；协同区/测试区文件按事实追加更新。

### 2.4 开发协同区定位说明（为什么保留）

模型间沟通分三类：① 任务指派——任务包本身即消息（设计区），派工 prompt 自包含一次性、不落盘；② 研究报告——调研报告已在设计区；③ **工作证据**——审核结论、执行自测、验证记录必须持久化：无证驳回、驳回轮次与 >3 轮裁决、上下文压缩后的证据恢复、责任追溯全靠它。故协同区保留，去掉"待发消息"语义，定位为状态机 + 证据区。

## 三、状态机

### 3.1 完整状态枚举

```text
待启动                          ← 任务包生成后的初始态（多包时未激活包停于此）
# 设计阶段（9 态）
需求沟通中 → 同类产品搜索中 → 调研中 → 方案设计中
→ 待可行性复核（按风险触发）→ 原型制作中 → 待设计确认 → 方案已定稿
→ 任务包生成中
# 开发阶段（7 态）
待审核 → 待修订 → 执行中 → 待验证 → 待代码审查 → 待构建 → 待人工测试
# 验收阶段：修复循环（5 态）+ 收尾
修复包生成中 → 修复中 → 待修复审查 → 待调度员检查 → 待构建更新 →（回 待人工测试）
收尾中（产品级，记于最后一包）→ 已完成
```

`待推送` 保留供「仅开发」旧任务兼容；新产品设计全流程任务收尾走 `收尾中`。

### 3.2 设计阶段转移表

| 当前阶段 | 负责方 | 必写产出（落点） | 合法后继 |
|---|---|---|---|
| 需求沟通中 | 调度员⇄用户 | 01_需求说明文档.md | 同类产品搜索中 |
| 同类产品搜索中 | 调度员 | 02_同类产品调研清单.md（用户可增删） | 调研中 |
| 调研中 | 研究员×N | 03_调研报告/<产品>.md 每产品一份 | 方案设计中；单份不达标→重派该产品 |
| 方案设计中 | 调度员 | 04_产品设计方案.md vX.Y（+05_分模块设计/） | 待可行性复核（高风险）/ 原型制作中 |
| 待可行性复核 | 审核员 | 协同区 过程记录/01_计划审核.md（复核意见） | 通过→原型制作中；不通过→方案设计中 |
| 原型制作中 | 调度员 | 原型/index.html + 自检留痕 | 待设计确认 |
| 待设计确认 | 用户 | 06_设计定稿记录.md（含顶部固定块 + 决策清点段） | 通过→方案已定稿；否决→见回退表 |
| 方案已定稿 | 调度员 | 定稿版本锁定 | 任务包生成中 |
| 任务包生成中 | 调度员 | 任务包/<TP>/01、02 + 协同区状态.md（初始 待启动）+ 预算台账 | 待启动（全部包生成完毕） |

> **设计决策清点**：位于 方案设计中→原型制作中 之间的交互态子步骤，**不新增状态**；三档可选（跳过/轻量/标准），协议见第九节。关卡1 提交物含 06 决策清点段。

### 3.3 开发阶段转移表

| 当前阶段 | 负责方 | 必写产出（落点） | 合法后继 |
|---|---|---|---|
| 待审核 | 审核员 | 协同区 过程记录/01_计划审核.md（计划审核意见） | 通过→执行中；驳回→待修订 |
| 待修订 | 调度员 | 任务包 01/02 原地修订 + 文末修订记录 | 待审核 |
| 执行中 | 开发员 | 任务包要求的代码改动（仅 02-代码/）+ 过程记录/02_执行与自测记录.md（自测附真实命令输出）+ 本地候选 commit | 待验证 |
| 待验证 | 调度员 | 过程记录/03_验证审核.md（对照验收标准逐条结论；无证驳回） | 通过→待代码审查；驳回→执行中 |
| 待代码审查 | 审核员 | 过程记录/04_代码审查.md（检查清单逐条 + 影响范围记录 + 复杂度发现小节 + 改动面清单） | 通过→待构建；驳回→执行中 |
| 待构建 | 调度员 | 构建产物 + 测试入口说明（05-交付/安装包/<版本号目录>/） | 待人工测试 |
| 待人工测试 | 用户 | 04-测试/<TP>/测试记录-YYYYMMDD.md | 报问题→修复包生成中；通过→已完成（本包）；最后一包通过→收尾中 |

### 3.4 验收阶段转移表（修复循环）

| 当前阶段 | 负责方 | 必写产出（落点） | 合法后继 |
|---|---|---|---|
| 修复包生成中 | 调度员 | 任务包/TP-修复N/01、02 + 协同区同名目录 | 修复中 |
| 修复中 | 开发员 | 修复代码 + 自测证据 + 候选 commit（过程记录/02） | 待修复审查 |
| 待修复审查 | 审核员 | 修复代码审查（记录于修复包过程记录，含复杂度小节） | 通过→待调度员检查；驳回→修复中 |
| 待调度员检查 | 调度员 | 检查记录（复核实测证据） | 通过→待构建更新；退回→修复中 |
| 待构建更新 | 调度员 | 更新产物 + 测试入口说明更新（05-交付/安装包/版本号目录） | 待人工测试（复测） |
| 收尾中 | 调度员 | 服务器更新记录 + push 记录 + 文档更新（含 ponytail-debt 扫描）+ 产品级收尾记录（并入最后一包 04-测试/验收结论.md） | 已完成 |

修复循环纪律：修复代码同样只能由开发员写、同样形成候选 commit；**修复后必经审核员代码审查**（同一候选 commit 绑定）；同一问题修复 >3 轮仍失败 → 生成决策简报交用户裁决（质量裁决，与预算无关——修复包不设预算上限，见第四节）。修复包过程记录为 02/03_修复代码审查/04_调度员检查 三份（01 计划审核不适用）。

### 3.5 回退规则

| 不通过环节 | 回退到 | 必须声明失效 |
|---|---|---|
| 单份调研报告不达标 | 调研中 | 该产品报告缺失项，重派研究员 |
| 审核员可行性复核 | 方案设计中 | 受影响的设计假设 |
| 关卡1 设计确认 | 原型制作中 / 方案设计中；方向性变化回 需求沟通中 | 旧方案版本与相关原型页面 |
| 计划审核 / 验证 / 代码审查 | 待修订 / 执行中（沿用现有规则） | 现有失效声明规则不变 |
| 修复审查 / 调度员检查 | 修复中 | 审查不通过项清单 |
| 用户复测仍有问题 | 修复包生成中 | 旧修复结论 |
| 测试暴露需求性错误 | 需求沟通中 或 方案设计中 | 定稿版本、任务包及相关审核结论（并触发第九节决策清点回退重跑规则） |

### 3.6 单一状态源与状态头字段

- `03-开发协同/<TP编号>-<名>/状态.md` 顶部固定格式块是全流程唯一机器状态源，任务包生成时建立，初始 `当前阶段 = 待启动`。
- 状态头字段：当前阶段 / 当前环节负责方 / 任务类型 / **流程类型**（产品设计全流程 / 仅开发，缺省仅开发）/ **设计目录**（指向 `01-设计/<产品任务>/任务包/<TP编号>-<名>`）/ 本环节驳回轮次 / 候选commit / 下一步 / 必读文件 / 最近更新 / 阻塞待办。**不含预算计数字段**——预算记账载体是 预算台账.md（第四节）。
- 设计/验收阶段为交互态，调度员对话推进并维护状态，不建 goal；开发阶段才由 `enter_auto_mode` 建 goal，**goal 粒度 = 单包**。
- **多包管理（串行）**：任务包生成时全部包初始 `待启动`；激活 = 调度员在交互态核查前置包（02 中标注的依赖前置）已全部 `已完成` 后，将当前包状态置 `待审核`，再经关卡2 授权启动。包间衔接全部走交互态，**不存在 goal 内跨包推进逻辑**。
- 仅开发旧任务：状态头无 设计目录 字段，任务包文档仍在 `03-开发协同/<任务>/开发计划/`，行为完全不变（enter_auto_mode 走仅开发兼容路径）。

### 3.7 驳回与裁决规则

- **驳回机制**：审核不通过须写明原因，回退上游修复后重审；回退时必须声明哪项已有结论因此失效、需从哪个环节重新执行。普通驳回原因只写过程记录中的审核意见文档，不重复记录。
- 同一环节最多 3 轮；同一环节驳回超过 3 轮 → 由负责模型生成**非技术化决策简报**（记入 `决策记录.md`，分歧类：当前卡点、重复失败根因、方案一/二成本与风险、推荐方案及理由、是否建议缩小需求/换模型/请真人工程师介入）→ 交用户裁决（选方案/调整需求/更换模型/终止任务），并更新 `状态.md` 阻塞/待办字段注明时间。
- **需求变更流程**：开发中途需求变更 → 记入 `决策记录.md`（变更类）→ 状态回 `待修订` → 调度员修订任务包 → 已做的验证/审查/测试结论按需声明失效并重新执行受影响环节（受影响分支需重跑第九节决策清点，已清零分支保留）。

## 四、预算口径（次数台账 + token 统计）

> 预算口径说明（用户为 Coding Plan 订阅、不按量付费）：**硬上限 = C/B 运行次数 + 调度员工作轮三项；统计信号 = token 用量（不作停机依据）；全程无费用概念**（否定式表述如「不统计费用」「不作金额换算」允许存在）。
> 控制原理：消耗主体是子代理运行（C 一次大上下文会话），不是调度员轮数；轮数已由「前景阻塞派工」恢复为工作步计数，见 3.7 与第九节。**控制手段 = 三种**：① 开发/验收阶段 B/C 派工一律前景阻塞（消除空转轮）；② 预算块 + 预算台账（次数硬上限）；③ 可选真实 token 计量（仅统计）。

### 4.1 预算基线（03-开发协同/预算基线.md）

- 用户维护的默认预算档，开工时建一次；**不含任何价格内容**。
- 内置默认档（基线缺失时按此继续，并在预算台账标注「按规范内置默认档」）：
  - **C 运行 ≤4 次/包**（含初次执行）；
  - **B 运行 ≤4 次/包**（计划审核+代码审查合计；复杂度审查只加小节不加环节、不额外计数）；
  - **调度员工作轮 ≤24/包**；
  - 修复循环 ≤3 轮/问题（质量裁决，非预算上限）；
  - 研究员运行 ≤ 调研清单注明的批次上限（沿用 ≤5 并行分批）。

### 4.2 任务包预算块（02_开发方案与任务包.md 固定格式）

调度员按基线填写，关卡2 前用户可见可改：

```text
【预算块】
C 运行次数上限：4
B 运行次数上限：4
调度员工作轮上限：24
超限动作：停止推进 → 生成决策简报 → 用户裁决
（无费用项：订阅制不按量付费；token 用量仅入台账统计，不作停机依据）
```

**修复包（TP-修复N）只统计不控制**：不填预算块上限，台账照记逐次运行与 token 用量，供用户自行管理；同一问题 >3 轮修复裁决机制保留。

### 4.3 预算台账（03-开发协同/<TP>/预算台账.md，机器可读）

复用状态.md 的"顶部固定块"模式：

```text
任务包：<TP编号>-<名>
预算块引用：01-设计/<产品任务>/任务包/<TP>/02_开发方案与任务包.md §预算块
上限：C运行≤4 / B运行≤4 / 工作轮≤24（仅三项硬上限；token 用量仅统计，不作停机依据）
当前累计：C运行=0 / B运行=0 / 工作轮=0 / token用量=—（第 3 层计量启用后填）
最近更新：YYYY-MM-DD HH:MM
---
| 时间 | 环节 | 模型 | 结论 | 累计C运行 | 累计B运行 | 累计工作轮 | token用量 |
|---|---|---|---|---|---|---|---|
```

### 4.4 判定规则

- 调度员**每轮开工先读台账固定块对照预算块**：C/B 运行次数、工作轮为**硬上限**——任一超限 → **立即停止推进**（goal blocked）+ 非技术化决策简报（复用 >3 轮机制）→ 用户裁决。
- **token 用量仅统计参考**：任何用量水平都不构成停机依据（硬上限只看次数/轮数）。token 用量硬上限仅待第 3 层计量落地且口径可信后可选开启。
- **计次规则（派工即计次）**：凡 B/C 派工点火即计一次运行，**含异常返回与用户中断**；恢复轮对照过程记录与 git log 对账补记漏记（中断条目照记「中断」）。
- token 用量列：第 3 层计量启用前填「—」；启用后按 provider 上报值填写（无上报时按 4 字符/token 估算并标注）；**token 计量不可用时退回纯次数台账**，流程不受影响。
- **全程无费用概念**：台账/预算块/规范相关表述不出现费用/价格折算；「不统计费用」类否定表述照抄允许。

## 五、任务包串行

1. **任务包打包策略**：适合一起开发的功能打成一个包（内聚模块/页面组）。无法合并的多包按依赖排序**串行推进**：一次只开发一个包，该包 04-测试 验收结论落盘（状态 已完成）后才激活下一包。
2. **授权范围**：一次「开始自动推进」授权**当前一个任务包**；包间不存在自动衔接，下一包由用户在人工测试通过后指示启动。
3. **初始态与激活**：任务包生成时全部包初始 `待启动`；激活 = 调度员在交互态核查前置包（02 中标注的依赖前置）已全部 `已完成` 后，将当前包状态置 `待审核`，再经关卡2 授权启动（enter_auto_mode 机器校验）。
4. **goal 粒度 = 单包**：enter_auto_mode 仅做单包校验；系统内不存在一包未通过人工测试（验收结论落盘）即开发下一包的路径。
5. **多包识别提示**：调度员开工/恢复时扫描各包状态，本包 已完成 且存在 待启动 包 → 对话提示用户可启动下一包。

## 六、验收阶段协议（修复循环与收尾）

1. **发测试**：调度员把待测试功能说明（测试入口、功能点、预期表现、已知限制）随构建产物发用户，状态 `待人工测试`；测试入口说明随安装包走（05-交付/安装包/版本号目录）。
2. **报问题**：用户对话直接描述问题；调度员确认（复现路径、期望 vs 实际）并分级：**修复级**→修复循环；**任务级**→升级开发阶段全流程（审核员审核后开发）；**需求级**→回设计阶段，声明定稿版本失效。用户每轮实测记录落 `04-测试/<TP>/测试记录-YYYYMMDD.md`。
3. **修复循环（含审核员）**：调度员生成修复任务包（`任务包/TP-修复N/`）→ 派开发员修复（自测+候选 commit，修复 diff 最小化）→ **审核员修复代码审查**（含复杂度小节；驳回回修复中）→ 调度员检查（复核实测证据，有问题退回重改）→ 构建/更新 → 再次提交用户测试。修复包每次派工记入 `预算台账.md`（只统计、不设上限）。
4. **本包关闭**：用户确认本包通过后，调度员写 `04-测试/<TP>/验收结论.md`（含**债务清单**段），状态置 `已完成`。
5. **串行衔接**：存在下一包时，用户指示启动 → 调度员核查其 02 标注的依赖前置包全部 `已完成` → 将该包状态 `待启动→待审核` → 回关卡2 授权后 `enter_auto_mode`。
6. **收尾（最后一包）**：用户确认通过并明确指令后，调度员按序执行：① 更新服务器（按项目既定部署方式；无目标服务器则跳过并记录）；② push git 远程仓库（失败或远程有变更→暂停报告，不自行 pull/merge/rebase）；③ 更新文档（README/操作手册/设计文档版本）+ **ponytail-debt 扫描**（汇总 `ponytail:` 注释，标注无升级路径的腐烂风险）；④ 产品级收尾记录并入最后一包 `04-测试/<TP>/验收结论.md`，状态 `已完成`，关闭产品任务。

## 七、验收硬规则与人工关卡

**人工关卡：**

| 关卡 | 时机 | 用户确认内容 | 未通过去向 |
|---|---|---|---|
| 关卡1 · 设计确认 | 04 方案 + 原型提交后 | 产品范围、核心流程、功能与规则、原型页面与关键状态；确认后写 06 定稿记录（固定块锁定版本号） | 按回退表逐级回退 |
| 关卡2 · 开发授权 | **每个任务包**齐备并激活后 | 用户明确说「开始自动推进」；设计确认 ≠ 开发授权；**一包一授权** | 不启动，继续对话 |
| 关卡3 · 收尾授权 | **最后一包**用户测试通过后 | 用户确认「测试通过」并明确指令收尾；push 失败或远程有变更时暂停报告 | 继续修复循环 |

**条件关卡 · 审核员可行性复核**（任一成立即触发）：改造既有系统核心流程；复杂权限/敏感数据/数据迁移；多外部系统或不稳定接口；架构替换/核心依赖升级/部署方式变化；高成本或高失败代价。审核员只写复核报告（落协同区过程记录），问题退回调度员。

**验收硬规则：**
- **无证驳回**：自测/验证结论只写"通过"无真实命令输出 → 直接驳回；
- 修复后必经审核员代码审查；同一环节 >3 轮出决策简报；
- **验收结论（含债务清单）落盘后才允许 已完成**；收尾必须用户明确授权；
- push 必须用户明确指令，失败或远程有变更时暂停报告，不自行 pull/merge/rebase。

## 八、ponytail 规则（最小实现纪律）

- **六档阶梯**（开发员写代码时逐级停靠，第一档适用即止）：需求不存在（YAGNI）→ 标准库 → 平台原生 → 已装依赖 → 一行代码 → 最小实现。
- **`ponytail:` 注释约定**：故意简化处写 `ponytail:` 注释，说明天花板与升级路径（如 `# ponytail: 全局锁，吞吐成问题再换每账号锁`）。
- **最小可运行检查**：非平凡逻辑（分支/循环/解析/安全性路径）留下**一个**最小可运行检查（assert 式 `demo()`/`__main__` 自检或一个小测试），随自测证据提交；平凡一行代码不需要测试。
- **复杂度审查小节**：审核员代码审查与修复审查各含一个「复杂度发现」小节（delete/stdlib/native/yagni/shrink 五标签 + net 行数结论）；**只加小节不加环节，不占额外 B 运行次数**（预算块不动）。
- **收尾债务清单**：收尾时 ponytail-debt 扫描 `ponytail:` 注释 → 债务清单写入验收结论.md；标注无升级路径的腐烂风险。
- **边界**：校验/安全/可访问性/显式需求**绝不偷懒**（When NOT to be lazy）；调度员/研究员不加载 ponytail；ponytail 不砍流程自身（YAGNI 面向 02-代码/ 产品代码，三阶段五区是个人使用的控制面，不反向瘦身）。

## 九、设计决策清点协议（grill-me）

> **机制说明**：本协议由调度员 persona 注入实现（注册期生效），**不直接加载外部 skill**——与 ponytail 融合方式一致。skill 不在会话技能目录，运行时加载不可依赖。

**定位**：04 方案（含 05 分模块设计）产出后、原型制作前的交互态子步骤；高风险任务在可行性复核通过后执行。不新增状态机状态；用户可随时说「跳过」。

**三档（用户选，缺省标准）**：

- **跳过**：用户直接进入原型/关卡1；
- **轻量**：只清零 01「待确认问题」+ 04「风险与待决策事项」两个清单；
- **标准**：完整决策树覆盖（顶层 3~6 分支 + 各分支子决策）。

**协议六条**：

1. 先列出顶层决策分支（3~6 条），**最基础的先问**（其余分支常依赖它）；
2. 逐分支问到底、子决策按依赖顺序；分支清零再进下一分支；
3. **每问先给推荐答案再问用户**，等用户回答再继续；
4. **能自查的不问**：调研报告、现有代码（codegraph）、05 分模块设计能回答的，自查解决并记录依据；
5. 停止条件：全部分支解决、无「it depends」；未解决项显式列入 06「未清零项」并标注依赖与阻塞；
6. 敲定的决策**实时写入 决策记录.md**（grill-with-docs 落盘纪律），会话结束时汇总进 06 决策清点段。

**边界**：决策清点是**产品决策对话**（调度员⇄用户）；技术可行性归审核员 B 复核——grill 不替 B 问技术细节，B 不替用户做产品取舍。

**回退重跑（与第三节回退表衔接）**：需求级问题回退设计阶段时，重跑受影响分支的决策清点，**已清零分支保留**。

**中断恢复**：交互态随时续问；已清零分支已写入 决策记录.md 即持久，无需重来。

**输入清单**：01「待确认问题」与 04「风险与待决策事项」是决策清点的输入清单，进入决策清点时逐条清零（每问先给推荐答案），不再停留在"记着以后再问"的被动状态。

| `03-开发协同/过程记录/04_代码审查.md` | 同上 | 检查清单 + 影响范围 + **复杂度发现小节** + 改动面清单 |
| `04-测试/测试记录-YYYYMMDD.md` | `04-测试/<TP>/` | 功能点/结果/问题（现象/期望/复现路径） |

## 十一、文档惯例

### 11.1 状态文档

`状态.md` 每次阶段变更时更新，**顶部固定格式块**（唯一机器解析源，自动推进模式只解析该块；正文其余供人读）：

```text
当前阶段：执行中
当前环节负责方：模型C
任务类型：大任务
流程类型：产品设计全流程        （或「仅开发」，缺省仅开发）
设计目录：01-设计/<产品任务>/任务包/<TP编号>-<名>   （仅开发任务可缺省）
本环节驳回轮次：0
候选commit：（C 形成候选 commit 后填写）
下一步：C 按任务包执行并自测
必读文件：01-设计/.../任务包/TP/02_开发方案与任务包.md
最近更新：YYYY-MM-DD HH:MM
阻塞/待办：（如有）
```

- **本环节驳回轮次**：阶段前移到新环节时由写状态方清零；同一环节每驳回一次 +1。
- **候选commit**：C 每次形成新候选 commit 后更新；验证、审查、测试必须针对同一个候选 commit。
- **预算记账**：状态头**不设**预算计数字段——预算记账载体 = 预算台账.md（第四节）。
- **写盘纪律**：先写产出文档，最后更新状态.md；落盘用"写临时文件 + 强制移动"（Windows 用 `Move-Item -Force` 等价物，rename 不能覆盖已存在文件）。

### 11.2 交接块（每份任务包文档顶部固定）

```text
【交接块】
目标：一句话（本环节在做什么）
上一环节：A 已产出任务包 / B 已审核通过……
本环节要做的：一句话
关键输入文件：02_开发方案与任务包.md
上一环节已确认：验收标准可测试
未决问题：（如无写"无"）
下一步负责人：模型C
```

- 文档主体是"证据与记录"，交接块是"指令"，两者分开。
- 每个阶段完成时，负责模型必须在交接块写清：下一步谁做、做什么、读哪些文件、有什么坑。

### 11.3 决策记录

`决策记录.md` 仅追加四类条目（普通驳回不记录）：

```text
### YYYY-MM-DD HH:MM | 类型（变更/分歧/例外/裁决）
参与方：
背景：
各方意见/选项：
结论与理由：
```

### 11.4 过程记录（协同区，替代 v1.1 协同文档）

- 模型间审核意见与工作证据按 01_计划审核 / 02_执行与自测记录 / 03_验证审核 / 04_代码审查 四件落盘（命名体系 v2.0，**不再沿用 v1.1 的「开发计划/01~05」与「协同文档/」命名**）。
- 审核意见文档内容：通过/驳回结论 + 原因；驳回时按"已检查的影响范围 / 采用的检查方法 / 已执行的测试 / 未覆盖的区域 / 剩余风险"五要素记录，并声明失效结论与重审起点。
- 普通交接（阶段正常前移）不建文档，只更新 `状态.md` 与各文档交接块。

### 11.5 06 设计定稿记录固定块与决策清点段

06 顶部为状态.md 同款固定格式块（供 enter_auto_mode 机器解析）：

```text
---
文档：06_设计定稿记录
确认版本：vX.Y
确认日期：YYYY-MM-DD
设计目录：01-设计/<产品任务>
---
```

正文：已确认页面与流程；**决策清点段**（每分支：问题/推荐答案/最终决定/依据；未清零项清单——含依赖与阻塞；附一行机制说明：本协议由调度员 persona 注入实现、不直接加载外部 skill）；需修改内容；暂缓项；原型无法表达但开发必须实现的规则；自检附录。定稿后不得静默修改 04/05/原型；变更须升版本并在 06 声明失效范围。

### 11.6 版本规则与修订记录

- 任务包 01/02 **豁免版本递增**：原地修订 + 文末修订记录（日期+改动摘要+触发环节）；04/05/原型/06 适用「不覆盖、版本递增」（另存新版本号文件，原版本保留）。
- 每次构建产物放 `05-交付/安装包/<名>-v<版本>/`（目录 + zip），附测试入口说明。

### 11.7 项目看板维护规则

项目根目录的 `项目看板.md` = **项目级任务总览**（人读导航层），形态：

- **三区**：✅已完成 / 🔄进行中 / 📋待办，各含任务编号 + 内容 + 状态链接（定位到 `03-开发协同/<任务>/状态.md`）；
- **维护方**：调度员；更新时机 = 任务立项 / 阶段大迁移 / 验收关闭 / 裁决入账后；
- **与协同区 `任务看板.md` 分工**：项目看板 = 项目级人读导航（根目录，面向用户）；任务看板 = 协同区任务状态同步（面向流程）；两者都链接到任务目录；
- **权威性**：冲突以各任务 `状态.md` 为权威；
- 项目根缺失 `项目看板.md` 时，由调度员按模板集第十节 `项目看板.md` 模板补建。

## 十二、部署纪律

- 验收阶段「更新服务器」优先走**项目内部署脚本**（shell 执行）；**预设默认不挂部署工具**（如 ssh）。
- 需远程部署时按项目实施期决策挂载 ssh 类工具；**无部署目标时跳过并记录**（收尾清单中写「待人工执行」或跳过说明）。
- 部署通道不可用时：完成构建与 push，更新服务器步骤标记「待人工执行」并给出操作清单。

## 十三、与 v1.1 差异说明

| 维度 | v1.1 | v2.0 |
|---|---|---|
| 目录体系 | 四区（设计/代码/开发协同/交付） | 五区（+04-测试 用户实测区） |
| 角色 | A/B/C/用户 | 调度员/研究员/审核员/开发员/用户（新增研究员；工具名 subagent_researcher/reviewer/developer） |
| 阶段 | 需求→计划→执行→验证→审查→构建 | 三阶段：设计（9 态）→ 开发（7 态）→ 验收修复循环（5 态）+ 收尾 |
| 任务包位置 | `03-开发协同/<任务>/开发计划/` | **双区同名**：设计区 `01-设计/<产品任务>/任务包/<TP>/` + 协同区 `<TP>/`；状态头 `设计目录` 机器指针 |
| 预算 | 无 | 预算基线 + 任务包预算块（三项硬上限 4/4/24）+ 预算台账（派工即计次、token 统计、修复包只统计不控制、无费用概念） |
| 多包推进 | 无（隐含） | 任务包串行：初始 待启动、一包一授权、goal=单包、前置包核查后才激活 |
| 修复循环 | 修复中 → 待调度员检查 | 修复中 → **待修复审查（审核员）** → 待调度员检查 |
| 设计决策 | 关卡1 确认方案+原型 | + **设计决策清点**（三档；06 决策清点段；未清零项显式列出） |
| 文档命名 | 开发计划/01~05 + 协同文档/ | 任务包 01/02（设计区）+ 过程记录 01~04（协同区）+ 04-测试 记录/验收结论 |
| 06 定稿记录 | 无固定格式 | 顶部固定块含 `确认版本：vX.Y`（enter_auto_mode 机器解析） |
| 交付物 | 安装包 | 版本号目录 + zip（附测试入口说明）惯例化 |
