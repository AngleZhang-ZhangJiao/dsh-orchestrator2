# 自动开发调度器2.0 · 使用手册（v2.1）

> 面向非技术用户。你只需要：跟它聊天说需求、点几下确认、看它干活、做一次人工测试。
> 本手册对应插件包 `dsh-orchestrator2`（预设「自动开发调度器2.0」）**v2.8.0**，只在 **规范 v2.1 的项目**（六区 + 归档区目录体系）上使用。
> **版本边界**：规范 v2.0 项目 → 先按第 3.5 节「升级脚手架」升到 v2.1 再用本预设；规范 v1.1 项目（老项目）→ 请继续用「自动开发调度器」（1.0）。

## 一、安装

**方式一 · 插件安装（唯一权威方式，0.1.7 声明式预设机制）**

```bash
dsh plugin --profile web add link:/路径/dsh-orchestrator2
```

0.1.7 起预设走**声明式机制**：包内 `presets/agent-preset.patch.yml` 在 DSH 启动时直接把「自动开发调度器2.0」声明进组合树，**不再需要、也不再存在** `~/.dsh/.agent-presets/` 目录同步——升级插件（重新指向新版本包）即生效。

**每次更新后、重启 DSH 前，先做 headless 体检（必做，2 分钟）：**

```powershell
node "$env:APPDATA\npm\node_modules\@deepseek-ai\dsh\lib\bin.js" web --dump-config
```

三点全过才重启宣告：① 组合树里 `preset-orchestrator2` 在列（与其余预设一起，一般共 7 个）；② 零死引用（无 `workflow-worker-thread` 等宿主已移除的包名）；③ 插件注册指向新版本包（`profiles\web\node_modules\dsh-orchestrator2` = 新目录）。任一点不过，不要宣告「请重启」，先排查。（事故沉淀：一次跳过硬伤导致会话全挂，见 `04-测试/DSH运维问题记录-2026-09-26.md` 问题 3/4。）

> 旧版「方式二 · 裸目录拷贝到 `~/.dsh/.agent-presets`」随 0.1.7 移除，勿再用；从旧版本升级残留的 `~/.dsh/.agent-presets/` 目录可顺手删除。

**装好后 2 分钟确认：**

1. 新建会话 → 预设选择器出现「**自动开发调度器2.0**」，选中无报错；
2. 问它"你有哪些工具" → 清单含 `enter_auto_mode`、`budget_status`、`subagent_researcher`、`subagent_reviewer`、`subagent_developer`、`set_role_model`、`reset_role_model`、`inspect_role_models`；
3. 让它在新项目上完成一个小设计（见第四节）→ 说「开始自动推进」→ 它会先压缩一次上下文，然后自动开始干活。

**前置条件：** DSH web 部署；模型凭证由你自行配置（本包不含任何密钥）：研究员与开发员默认用 `deepseek-official/deepseek-flash`（降级 `openai-codex/gpt-5.6-luna`）、审核员默认用 `volcengine/glm-5.3`（降级 `openai-codex/gpt-6.1-sol`）——在 DSH 设置页或 settings.yaml 配好对应 provider 与密钥（见下「默认模型与档位」）。

**默认模型与档位（默认 + 降级，v2.7.0 起）**

| 角色 | 默认路由（provider / model） | 档位（reasoningEffort） | 降级路由 | 降级档位 |
|---|---|---|---|---|
| 调度员（主会话） | `kimi-coding/k3` | `max` | —（无自动降级） | — |
| 研究员 `subagent_researcher` | `deepseek-official/deepseek-flash` | `max` | `openai-codex/gpt-5.6-luna` | `xhigh` |
| 开发员 `subagent_developer` | `deepseek-official/deepseek-flash` | `max` | `openai-codex/gpt-5.6-luna` | `xhigh` |
| 审核员 `subagent_reviewer` | `volcengine/glm-5.3` | 未声明（provider 默认） | `openai-codex/gpt-6.1-sol` | 未声明（provider 默认） |

- **路由文件（v2.7.0 起）**：三角色的持久默认/降级路由存在 `<DSH_HOME>/orchestrator2/model-routes.json`（缺省 `%USERPROFILE%\.dsh\orchestrator2\model-routes.json`），**每次派工现读**——保存即对后续新派工生效；首次运行时按上表自动初始化；会话覆盖与子代理快照存在同目录 `sessions/<主会话ID>.json`。改路由**不再需要改 `agent.cordis.yml`**（yml 里的官方三角色钉模型行已删除）。
- **会话内临时改模（默认仅本会话）**：直接说人话即可，例如「把开发员换成 kimi-coding/k3」「审核员临时换成 volcengine/glm-5.3-flash」「恢复开发员的默认模型」——调度员会调 `set_role_model` / `reset_role_model`，只影响**当前主会话的后续新派工**（在跑的子代理保持派工快照不变）；换会话/重启后回到持久默认。
- **永久修改**：只有明确说到「**默认模型**」或「**降级模型**」才写持久文件，例如「把审核员的默认模型改成 volcengine/glm-5.3-flash」——保存成功后当前会话与新会话的后续新派工立即读取；本会话若已有显式覆盖，覆盖仍然优先（回执会告诉你哪些槽位没动）。
- **自动降级**：角色模型遇到 429/限流（RATE_LIMIT）或已确认可恢复的额度错误时，**直接**切到该角色的降级模型重试一次（不先同模型重试）；降级模型再失败即停止并报告，不循环切换；本会话保持降级，用户再改/恢复或新会话才重新尝试。认证错误、上下文超限、无效模型等非适用错误**不降级**；取消（你点了停止）优先于降级。
- **首版边界**：「仅下一次」一次性覆盖不支持——明确要求时会得到「首版不支持」提示且不改任何状态。查当前路由：让调度员用 `inspect_role_models` 列给你看。
- **预设层不能钉谁**：DSH 预设文件（`preset.yml`）只承载显示文本（名称/描述/排序），**无法声明会话模型**——调度员（主会话）用哪个模型，取决于全局 `agent-default-model` 设置或你**新建会话时选的那个模型**。想让调度员跑 `kimi-coding/k3` + `max`，请在新建会话时自行选择。
- **档位说明**：研究员与开发员同为 `deepseek-flash` + `max`（2026-09-30 第二项裁决把开发员由 `high` 抬到 `max`）；审核员 `glm-5.3` 与两条降级路由均不声明档位（provider 默认）。想改档位或换模型：在会话里说（仅本会话）或明确指定默认/降级（永久）；改完跑 `node 02-代码/orchestrator2/tests/suites/config-check.mjs`（T3e 装配断言）核验源码侧装配。

## 二、与 1.0 并存

- 1.0（预设「自动开发调度器」、插件 `dsh-orchestrator`）与 2.0 **同时安装、互不影响**；两个插件包各插各的 bundle、各同步各的预设目录，可同时安装、各自卸载。
- **选用规则**：规范 v1.1 项目（老项目）→ 用 1.0；规范 **v2.1** 项目 → 用 2.0（**v2.0 项目先升级脚手架**，见 3.5）。
- **同一项目不混用两个预设**：状态机与校验逻辑不同，混用会错乱。2.0 会话开工时如果发现项目里是 v1.1 规范（或没有规范文件），会按「保险丝三分支」处理（见 3.5），而不是硬跑。
- 1.0 预设与既有项目不受 2.0 安装影响。

## 三、新项目脚手架（规范+模板如何落位）

### 3.1 正常路径：空白新项目

2.0 的规范与全套模板随预设包提供（`presets/orchestrator2/spec/`，插件安装后位于 `profiles\web\node_modules\dsh-orchestrator2\` 下），新项目开工时：

1. 建好项目根目录（空目录 + `git init` 即可）；
2. 新建 DSH 会话，选「自动开发调度器2.0」预设，工作区指向该项目根；
3. 对它说：**「初始化 v2.1 脚手架」**——它会：
   - 把 `spec/项目目录及协同开发规范-v2.1.md` 复制到 **`00-项目管理/项目目录及协同开发规范.md`**（v2.1：规范本体入 00 区）；
   - 按规范第十节模板索引，把 `spec/templates/` 下的模板复制到位（`00-项目管理/`、`_任务模板/`、`01-设计/`、`03-开发协同/`、`04-测试/`、`05-交付/`、`90-历史归档/`）；
   - 把根级模板 `项目看板.md` 复制到**项目根目录**（项目级任务总览，以后它随任务状态自动更新，见第六节）；
   - 建 `03-开发协同/预算基线.md`（默认档：**小包** C≤4 / B≤4 / 工作轮≤24；大包见第六节；缺失时它按规范内置默认档继续，不用你操心）。
4. 之后就可以开始聊需求了（第四节）。

> 也可以手动复制：规范文件 + `spec/templates/` 整目录拷进项目对应位置即可。

### 3.2 v2.1 目录体系（六区 + 归档区）一览

| 目录 | 放什么 |
|---|---|
| `00-项目管理/` | **新增**：当前状态 / 产品路线图 / 任务索引 / 决策索引 / 发布批次规划 / 本区 README / **规范本体** |
| `01-设计/` | 需求 → 调研（或场景1 的现状分析）→ 方案 → 分模块 → 定稿 → 任务包 → 原型；另含 `技术调研/`（场景2 落盘区） |
| `02-代码/` | 产品本体（唯一代码区；场景1 下目标代码区由任务包指定） |
| `03-开发协同/` | 状态机 + 工作证据；**扁平化**：`计划评审-vX.Y.md` / `执行自测-YYYYMMDD.md` / `代码审查-vX.Y.md` 直放任务根（不再有 `过程记录/` 子目录） |
| `04-测试/` | 用户实测 + **新增** `测试基线/`、`全局回归/` 全局骨架 |
| `05-交付/` | 安装包 / 操作手册 / 演示方案 / 宣传材料 + **新增** `发布批次/` 与任务级 `构建记录-/推送记录-/部署记录-YYYYMMDD.md` |
| `90-历史归档/` | **改名**（原 `历史记录/`）：历史排期 / 废弃方案 / `旧目录映射.md`（旧路径解析依据） |

### 3.3 「保险丝三分支」——它对不同现状的反应

它开工第一件事是看项目根有没有规范，按三分支决策：

| 项目现状 | 它的动作 |
|---|---|
| 项目根**有 v2.x 规范** | 直接进主流程（新产品开发）（v2.0 会先提示升级，见 3.5） |
| 项目根**无规范、且是空白/新项目** | 走脚手架初始化（复制规范 + 模板 → 3.1） |
| 项目根**无规范、但已有代码系统**（有源码目录/依赖清单/构建配置任一） | 进 **场景1「修改已有系统」模式**：先向你确认 → 补建 v2.1 六区脚手架（**不搬运、不改造你的老代码**）→ codegraph 索引建在**项目根** → 若无 `.git` 会提示你，确认后**代你 `git init` + 首次 commit** |

> 「场景2 技术调研储备」**不做**环境自动探测（避免误触发）：只在你表达「技术调研 / 调研储备 / 摸底某技术方向」这类意图时，它复述「主题 + 形态（独立调研，不进开发）」请你确认后才进入（见第五节 B）。

### 3.4 老系统改造（场景1）与主流程的差别

修改已有系统的功能/bug 时，设计阶段走**变体链**：`需求沟通中 → 现状研究中 → 方案设计中 →（默认触发可行性复核）→ 设计决策清点 →（原型）→ 待设计确认 → 定稿 → 任务包`。开发/验收阶段与新产品**完全相同**。

- 「现状研究中」= 派研究员只读分析你的老系统，产出《系统现状分析》（技术栈/关键调用链/现状详查/影响面初判/未解决问题/安全纪律声明）；**系统太大时会按模块分批，每批一份，你逐批确认继续**。
- **设计链档位**立项时选：**短链**（小改）或**标准**。短链最小产物 = 需求说明 + 系统现状分析 + 轻量方案 + 定稿记录 + 任务包；**豁免**分模块设计与原型，决策清点默认轻量档。
- **目标代码区**：确认现状时你圈定允许改动的源码目录（缺省=仓库根扣掉六区目录）。任务包会据此列出**影响面清单**；开发员改动越界 = 范围漂移，立即停工上报你裁决。

### 3.5 升级脚手架（v2.0 项目 → v2.1）

规范 v2.0 的项目在 v2.1 预设下**不会报错**（旧阶段值全部保留），但五态流水线语义会对旧七态状态头产生**语义错位**。所以：对 2.0 会话说 **「把这台项目升级到 v2.1 脚手架」**——它会按 v2.1 目录体系补齐 `00-项目管理/`、`04-测试/测试基线/`、`全局回归/`、`05-交付/发布批次/`、`90-历史归档/`，并把规范本体换成 v2.1；在途任务按旧记录名走完即可（旧名映射见 `90-历史归档/旧目录映射.md`）。

## 四、日常使用（设计 → 下令 → 推进 → 人工测试）

### 4.1 设计阶段（对话模式）

**新产品开发**：

```
聊需求 → 出《需求说明》→ 搜索同类产品列出《调研清单》（你可增删）
→ 派研究员并行调研（各出一份报告）→ 出《产品设计方案》
→ 设计决策清点（它开场先问你档位：跳过/轻量/标准，关键问题先给推荐答案，你逐条拍板）
→ 做可点击原型 → 关卡1：你确认设计（方案+原型+决策清点）＝**开发授权**
  （它同场给你分流选择「确认即开工 / 仅定稿存档」+ #32 模型配置提示，仅首包一次）
→ 写《设计定稿记录》（锁定版本号）
→ 功能分组生成任务包（标注档位：小包/大包，你确认预算合计）→ 「确认即开工」则自动开工
```

**修改已有系统（场景1）**：把上面第 2 步换成「现状研究中」（见 3.4），其余相同。

> **档位提示**：设计决策清点**开场就会问你**要哪一档（v2.1 变化：不再默认标准）——想省时间选「轻量」，想彻底聊清选「标准」，赶原型选「跳过」。

### 4.2 下令开发（关卡1＝开发授权 · 一次授权多包连跑）

**新流程（#33 授权合并）**：设计定稿确认的那一刻就是**开发授权**——你**不再需要**另说一次「开始自动推进」。

- 它把设计定稿交给你时，会给你**两个选项**：
  - **「确认即开工」**：任务包生成完成后它自动核查前置、激活首包并开始推进——你只要坐着看；
  - **「仅定稿存档」**：只写定稿记录，停在待启动，等你以后发话。
- 同一时刻它会附上 **#32 模型配置提示**（**仅首包问一次**）：展示研究员/审核员/开发员各自的钉模型 + 推理档位 + 主会话模型，问你是否要改。要改的话它会说明生效路径（派开发员改 `agent.cordis.yml`）——**修改从下一会话生效，本次推进沿用现配置**。
- 选「确认即开工」后它会自动：计划审核（审核员）→ 开发（开发员）+自测 → **审核（审核员一次完成：证据核验 + 代码审查）** → 构建出安装包；
- 到达**「待人工测试」**后自动停，把「测试入口说明」交给你——这是硬停止点，等你实测。

> **v2.1 变化（连跑）**：任务包按「**能否构成一次有意义的人工测试**」切分；**两次人工测试之间的所有包全自动连跑**，包间不再要你说授权；**你测过之后它就自动放行下一包**。
> **刹车仍在**：驳回超过 3 轮 / 范围漂移 / 预算触顶 → **立即停机并给你一张决策简报**；你**随时可以喊停**（对话里说一句「停」）。
> **人工介入点（收敛为四处，授权合并后口径）**：设计定稿确认（含分流与模型提示）+ 各次人工测试 + 异常裁决 + 收尾授权。
> **兼容说明**：旧的两步走（定稿确认 ≠ 开发授权，之后要另说「开始自动推进」）已作废；说这句仍然有效，等同授权。

### 4.3 人工测试与验收

- 你的实测记录落 `04-测试/<任务包>/测试记录-YYYYMMDD.md`；
- 有问题：直接在对话里描述（现象/期望/怎么复现）→ 它生成修复包 → 修复 → 审核员审查修复 → 它核查证据 → 出新安装包 → 你再测；
- 本包通过：它写《验收结论》（含债务清单），本包状态 = 已完成；**然后自动核查并放行下一包**（无需你再说授权）；
- 最后一包通过：你先明确收尾授权，它执行收尾（部署/推送/文档更新），产品任务关闭。

## 五、两种场景的使用说明（附走查示例）

### A · 场景1：修改已有系统的功能/bug

**怎么开始**：新建会话，工作区指向**老系统仓库根目录**，说一句需求，例如「这个老项目里，登录失败时的错误提示不清楚，帮我改清楚」。它发现"有代码但没有规范"→ 按保险丝三分支进场景1。

**走查示例（一轮完整流程）**：

| 步骤 | 你说/它做 | 你会看到 |
|---|---|---|
| 1 | 它问：「检测到既有代码系统，是否进入『修改已有系统』模式？」 | 你答「是」 |
| 2 | 它在项目根补建六区脚手架（不碰你的老代码），提示「未发现 .git，是否代你 git init + 首次 commit？」 | 你答「是」→ 仓库有了基线 |
| 3 | 它问设计链档位 | 小改说「短链」，大改造说「标准」 |
| 4 | 派研究员只读分析 → 出 `01-设计/<系统名>-<主题>/02_系统现状分析.md` | 你读一遍，确认现状对不对（系统大时它分批给你看） |
| 5 | 出轻量方案 →（默认触发可行性复核）→ 决策清点（短链默认轻量档） | 逐条拍板 |
| 6 | 关卡1：你确认设计与现状 | 它写《设计定稿记录》 |
| 7 | 生成任务包（含**影响面清单**：允许改哪些文件） | 你过目档位与预算 |
| 8 | 你说「开始自动推进」→ 审核 → 开发 → 审查 → 构建 | 到「待人工测试」停下 |
| 9 | 你实测 → 通过 | 写验收结论，本包完成 |

**观察点（本包干跑不覆盖，靠你实测确认）**：
- **目标代码区越界拦截**：若开发员改动了影响面清单外的文件，B 环节应拦下并把该阶段视同未完成（你可以直接问它「本轮 git status 里有没有越界文件」）。
- **codegraph 降级口径**：若项目里没有 `.codegraph/`（索引不可用），现状分析报告应**明确注明「未使用 codegraph」**，并说明改用全文搜索 + git 分析替代——**不允许假装用了**。

### B · 场景2：技术调研储备搜索

**怎么开始**：说一句意图即可，例如「我想对『本地优先的同步框架』做个技术调研储备」。它**不做环境探测**，而是复述：「主题=本地优先同步框架；形态=独立调研，不进开发——确认吗？」你答「确认」，流程开始。

**走查示例**：

| 步骤 | 你说/它做 | 你会看到 |
|---|---|---|
| 1 | 方向确认 | `01-设计/技术调研/<主题>/01_调研方向确认.md`（业务需求/你给的技术路线/边界与脱敏注意） |
| 2 | 它拟首批清单（对象/链接/来源/调研价值/重点关注点/深度/批次） | `02_调研清单.md`，你确认或增删 |
| 3 | 派研究员并行调研（≤5/批） | 每对象一份 `03_调研报告/<对象>.md`（含**技术路线对比矩阵** + **同类拓展候选**） |
| 4 | 汇总上一批的「同类拓展候选」去重后，**建议下一批（附规模与理由）** | 你确认/增删/喊停；批次号递增 |
| 5 | 你随时可说「进入汇总」 | 它写 `04_调研汇总报告.md`（对比矩阵汇总 + 分场景推荐 + 未解决问题 + 报告索引）**并当面向你汇报** |
| 6 | 状态 → 已完成 | **流程结束**（要落地实施 → 你另立开发任务走主流程） |

**要点**：本流程**不建推进目标、不进开发阶段、不会自动生成任务包**（封闭性）；预算台账**只统计不控制**（不设上限）；它与在跑的开发任务可以并行，互不抢占。

## 六、预算查看（次数台账 + token 统计）

2.0 的预算是「**次数 + 轮数**」而非金额（你是订阅制，不按量付费，全程无费用概念）：

- **按包复杂度分档**（v2.1 新增）：**小包** 开发员运行 ≤4 次 / 审核员运行 ≤4 次 / 调度员工作轮 ≤24 轮；**大包** ≤8 / ≤8 / ≤48。任务包生成时它标注档位并请你确认；没有标注时按小包算。
- **修复包与场景2 技术调研**：**只统计、不设上限**（同一问题修 >3 轮会出决策简报请你裁决）。
- **看次数**：打开 `03-开发协同/<任务包>/预算台账.md`——顶部固定块是「当前累计」，下面每行是一次运行（时间/环节/模型/结论/token 用量）。
- **台账新列与状态词（v2.3.0）**：每行还登记 `runId`（本次派工标识）/ `attempt`（第几次尝试）/ `派工前阶段 → 结算后阶段` / `candidateCommit`，台账顶部有一行「账本身份」（任务编号 + schema 版本 + 目录 + 流程类型）——它用来防「台账放错任务目录」这类串档；结论列在中文摘要后带一个状态词，如 `通过〔DONE〕`。
- **子代理返回六态（v2.3.0）**：开发/审核子代理每次返回必是六态之一——**DONE**（完成）/ **DONE_WITH_CONCERNS**（完成但有疑点，疑点必须写进执行自测的「concerns」小节）/ **NEEDS_CONTEXT**（缺上下文）/ **BLOCKED**（被阻塞）/ **FAILED**（失败）/ **INTERRUPTED**（被中断）。前两种要求任务阶段确实前进了一步；后四种「没前进」是合法结果（照样计一次数、写明原因、释放锁），它会按失败与中断路径处置重派，**不会用同一模型原样重试**。
- **看 token 用量**：在对话里对它说 **「查一下 token 用量」**（它调用 `budget_status` 工具），它会列出本项目各会话的输入/输出/合计 token 数——仅作统计参考，**任何用量水平都不会让它停机**；计量源不可用时它会明说「以预算台账次数记录为准」，不编数据。
- **触顶行为**：任一硬上限超限 → 它立即停，生成一张通俗决策简报（继续/收缩范围/换模型/人工接管）请你拍板，绝不自动继续。
- **看总体进度**：打开项目根目录的 `项目看板.md`——✅已完成 / 🔄进行中 / 📋待办三区列出所有任务（编号+内容+链接到各任务 `状态.md`）。它由它（调度员）在任务立项、阶段大迁移、验收关闭、裁决入账后自动更新；项目级快照看 `00-项目管理/当前状态.md`，流程内部状态同步看 `03-开发协同/任务看板.md`；**冲突时一律以各任务 `状态.md` 为准**。

## 七、中断恢复与残留锁

- 任何时候你可以打断它（关会话、点停止都行）：前景派工时中断信号会传到子代理，时间随停。
- 恢复：新开会话（还选同一个预设，工作区不变）→ 说一句 **「继续」**。
- 它会自动做三件事再干活：
  1. **清残留锁**：任务目录里的 `.lock` 文件超过 30 分钟、或对应子代理已经不活跃 → 自动删除（不会有人卡着不让它跑）；
  2. **对账补记预算台账**：对照工作证据与 git 历史，把断点前漏记的运行次数补上（中断那次记为「中断」）；
  3. **四方一致核对 + 续跑建议（v2.3.0）**：它会自动比对「台账身份行 / 各任务状态头 / 候选 commit / 工作证据文件」四方是否一致，不一致会先报出来再动手；同时给出续跑建议——已经有过「通过」结论的环节不会重派（不重花你的钱/时间），直接指向第一个还没结论的环节；
  4. 按 `状态.md` 从断点继续推进。
- 设计阶段的决策清点被打断也没关系：已拍板的分支都写进了《决策记录》，随时接着问，不用重来。

## 八、开发期回归（插件源码侧；普通用户可跳过）

> 本节面向**改这个插件本身的人**（维护者/开发员），不是普通用户日常操作。

插件的源码在 `02-代码/orchestrator2/`，回归测试与夹具在 `tests/`（**不进交付包**，`package.json` 的 `files` 不含它、zip 也不含）：

```powershell
# 全量回归（推荐；自动重建夹具、采集基线、顺序跑 13 个断言套件）
node 02-代码/orchestrator2/tests/run-all.mjs

# 只跳过夹具重建（夹具已就位、想快一点）
node 02-代码/orchestrator2/tests/run-all.mjs --no-fixture

# 单跑某一个套件（自带 PASS/FAIL 明细与 pass=/fail= 汇总行）
node 02-代码/orchestrator2/tests/suites/t10-enum-cases.mjs
```

**分级**：14 个断言套件属「构建前必跑」（`run-all.mjs` 全跑即覆盖）；e2e fixture 干跑属「按需」（验证 `enter_auto_mode` 全路径矩阵：合法包接受 + 各类拒绝 + 04/06 层级）。

**数字口径**：每个套件末行 `pass=N fail=M`，并经 `tests/lib/test-harness.mjs` 落 `tests/.cache/results/<套件>.json`；`run-all.mjs` 读这些 JSON 求和打印「断言合计」——汇总数字逐件实测相加，可复算。

**目录**：`tests/suites/`（断言套件 + 规范生成器 + e2e 干跑）、`tests/lib/`（路径单一来源 `paths.mjs` + 结果记录 `test-harness.mjs` + 夹具助手 `scenario-utils.mjs`）、`tests/fixtures/`（夹具生成器 + T9 基线采集 + `t9-data/`）。夹具项目树与 `.cache/` 是**可重生成产物**，已 gitignore。
